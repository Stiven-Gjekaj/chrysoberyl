<objective>
Rasterize an SVG pair on the CPU through a new adapter crate, and render
every glyph from one font this repository carries rather than from the
machine that happens to run the tool.

Purpose: SRC-04 needs an SVG pair compared at the same quality as a raster
pair. DET-05 needs the host font database to be unreachable, not merely
unused. Both are adapter-level guarantees, so the engine never learns an
SVG existed.

Output: a `chrys-source-svg` crate, one pinned font with its licence, a
text-bearing fixture pair, and a CLI that sends an SVG file to the new
adapter.
</objective>

**Second commit: everything below, in one change.**

**The dependency pin.** Add to the workspace dependency table in the root
`Cargo.toml`:
`resvg = { version = "=0.48.1", default-features = false, features = ["text"] }`

Four of the five default features are dropped on purpose, and each for its
own reason. `system-fonts` is dropped because it is the feature that
compiles the host-font-database reader into the binary, and DET-05 says
that capability must not exist rather than must not be called. `svgz` is
dropped because no fixture is gzip compressed. `memmap-fonts` is dropped
because no font is read from a file at run time. `raster-images` is
dropped because the fixture is vector content only, and dropping it also
keeps `image`, `gif`, `image-webp` and `zune-jpeg` out of this crate's
graph entirely. Put the pin in the workspace table, not in the crate's own
manifest, so the guard plan 04-02 adds reads one line in the same file and
the same shape the existing `palette` guard already reads.

`resvg` re-exports `usvg` and `tiny_skia` at its own crate root, and
`usvg` re-exports `fontdb`. Declare no separate `usvg`, `tiny-skia` or
`fontdb` line anywhere: a second pin can drift from what `resvg`'s own
manifest already requires.

**The crate.** Create `crates/chrys-source-svg`, picked up by the existing
`crates/*` member glob. It declares `#![forbid(unsafe_code)]` and
`[lints] workspace = true`. Its `[dependencies]` are `chrys-source`
(path), `resvg` (workspace) and `thiserror` (workspace), and nothing else.
Its `[dev-dependencies]` are `chrys-source-raster` (path, for the
limits-agreement test plan 04-02 adds) and `png` (workspace, for the
renderer example Task 2 adds). Neither dev entry may appear under
`[dependencies]`.

**The pinned database.** Create `src/fonts.rs`. It holds the one
`include_bytes!` call in this workspace, reading
`"../fonts/NotoSans-Regular.ttf"`. That path is relative to `fonts.rs`'s
own directory, not to the manifest, which is the one thing about this
macro that does not follow Cargo's convention and the one thing that
breaks on the first build if it is written the other way. Expose
`pinned_fontdb()`, which builds a `fontdb::Database` with `Database::new()`
and fills it with exactly one `load_font_data` call on the embedded bytes.
`Database::new()` is documented as empty, so a database this function
returns holds one font and can hold no other. Say that in the function's
own doc comment.

**The options.** In `src/lib.rs`, build `usvg::Options` with `fontdb` set
to an `Arc` around `pinned_fontdb()`, and set `font_family` to the pinned
family's own name. `usvg::Options::default()` names a family this database
cannot supply, so a text node with no `font-family` of its own would
otherwise resolve to nothing rather than to a glyph this repository chose.
Read the family name out of the database rather than typing it from
memory: Task 3 turns that into an assertion.

**The adapter.** Define `SvgSource` holding an `SvgLimits`, with `new()`,
`with_limits(..)` and `Default`, matching `AnimationSource`'s shape.
Define `SvgLimits { max_width: u32, max_height: u32, max_alloc: u64,
max_file_bytes: u64 }`, defaulting the first three to the same numbers
`chrys_source_raster::DecodeLimits::default()` uses and `max_file_bytes`
to 8 MiB. Define `SvgError` with `thiserror`, carrying at least: the path
could not be read; the file is larger than `max_file_bytes`, naming both
numbers; the document did not parse, naming the parser's own message; the
declared canvas is larger than the limits, naming the width, the height
and the limit; and the canvas is empty. Plan 04-02 writes the tests that
prove the last three refuse rather than allocate; declare the variants and
the fields here, and enforce them here, so that plan adds tests rather
than reshaping a type or closing a hole.

Implement `Source for SvgSource`, and enforce every limit on the one path
rather than leaving a refusal for a later task. A tracer carries the real
error handling of the path it wires; an adapter that allocates a pixel
buffer from an untrusted declared size, even for one wave, is the exact
gap `DecodeLimits` and `AnimationLimits` already exist to close for the
other input families. Plan 04-02 writes the tests that prove each refusal
fires; the refusals themselves are here.

In order:

1. Read the file's declared length with `fs::metadata` and refuse above
   `max_file_bytes`, naming both numbers. This is the fast, clear refusal.
2. Read the bytes through `File::open` and `Read::take` bounded at
   `max_file_bytes` plus one, and refuse again if the read returned more
   than `max_file_bytes`. The second check is not redundant: a length read
   from metadata and a length read from the file are two measurements of
   two moments, and only the second one bounds what this process actually
   allocated. AGENTS.md records that a size is not a state.
3. Parse with `usvg::Tree::from_data`, mapping the parser's own error into
   the typed parse variant with its message kept.
4. Take `tree.size()`'s integer size and refuse before any allocation when
   the width or the height is above the limit, or when width times height
   times four is above `max_alloc`. `usvg::Options` carries no size-limit
   field of its own, which was read from that struct's full definition at
   research time, so this check is the only thing between a document
   declaring a million pixels a side and a `Pixmap` of that size.
5. Allocate a `tiny_skia::Pixmap` of that size, mapping the constructor's
   `None` to the empty-canvas variant.
6. Call `resvg::render` with an identity transform into the pixmap's
   mutable view.
7. Build one `Frame` from `Pixmap::take_demultiplied()` with `index: 0`
   and an empty `hints`, and return a vector of that one frame.

`take_demultiplied` is the whole of the alpha conversion. Write no
per-pixel divide loop: a hand-rolled divide needs its own zero-alpha case
or it divides by zero, and this one call is already correct there. Task 2
proves the conversion happened.

Do not override `load_named`. The default body pairs the one frame with
the file's own name, which is exactly right for a source that reads one
file into one frame.

**The sniff.** Create `pub fn looks_like_svg(path: &Path) -> Result<bool,
SvgError>`. It reads a bounded prefix of at most 1024 bytes through
`File::open` and `Read::take`, never the whole file: a sniff that reads
its whole input to decide whether to read its whole input is itself the
decompression-bomb surface every other adapter in this workspace already
guards against. Over that prefix it skips a UTF-8 byte-order mark if one
is present, then answers true only when both of two things hold: the first
byte that is not ASCII whitespace is a less-than sign, and the prefix
contains the four characters that open an SVG root element. The first
condition is what keeps a binary raster file out: a PNG's first byte is
0x89 and a GIF's is `G`, so neither can reach the second condition by
accident. An I/O error propagates as `SvgError`; it is never silently read
as false.

**The CLI.** Add `chrys-source-svg` as a path dependency of `chrys-cli`.
In `named_frames_for`, add a fourth branch after the `path.is_dir()`
branch and before the animation sniff: when `looks_like_svg(path)` is
true, load through `SvgSource::new()`. Putting the textual check first
means a non-SVG file is only opened through `image::ImageReader` after the
cheaper check has already said no. Update the function's own doc comment
to describe four branches rather than three.

ninth crate under `crates/`. `every_crate_in_the_workspace_forbids_unsafe_code`
asserts the walk found at least eight crate roots, and its own comment says

**The fixture.** Hand-write `tests/golden/formats/svg/base.svg`, 256 by
256, the same canvas every other fixture family in this repository uses.
It carries, all in one document:

- At least four saturated, high-contrast rectangles at four distinct
  positions, acting as the anchor edges phase correlation needs. A frame
  with one flat block and one changed patch is unsafe input for this
  engine, which phase 1 recorded twice.
- At least one curved path, so the phase's own goal statement about real
  curves is exercised rather than asserted.
- One linear gradient, confined to a band rather than covering the canvas,
  so smooth content exists without starving the correlation of edges.
- One shape whose fill opacity is not 1, so the fixture cannot pass the
  alpha handling for the wrong reason. A fixture opaque everywhere is
  byte-identical under both alpha conventions and proves nothing about
  either.
- Two text elements. One names the pinned family explicitly. One carries
  no font-family attribute at all, so the fallback path Task 3 asserts is
  exercised by the shipped fixture too, not only by an in-memory test.

Keep any XML comment header short enough that the root element tag still
falls inside the first 1024 bytes the sniff reads, and add one comment
line saying that constraint exists, so a later editor who lengthens the
header knows what they are about to break.

Copy it to `candidate.svg` and change exactly one thing: recolour one
rectangle from one saturated hue to a distant one. Change nothing else,
and in particular do not touch a text element: the text must be identical
on both sides so that criterion 3's digest is about the glyph rendering
rather than about a difference the fixture introduced. A recolour that
large is far above the antialiasing suppression floor, so it classifies as
a real change rather than being discarded.

**The tests.** Create `crates/chrys-source-svg/tests/svg.rs` with
`identical_svgs_produce_identical_frames`: load `base.svg` twice through
`SvgSource` and assert the two frames are equal field for field, then load
`base.svg` and `candidate.svg` and assert their pixel buffers differ.
Assert the frame is 256 by 256 and that its buffer length is width times
height times four. Reach the fixture with `env!("CARGO_MANIFEST_DIR")`
joined with `../..`.

Create `crates/chrys-cli/tests/svg_dispatch.rs` with three tests, each run
through `Command::new(env!("CARGO_BIN_EXE_chrys"))`, the pattern
`crates/chrys-cli/tests/digest.rs` already uses.

`an_svg_pair_reports_a_recoloured_region` runs the binary over the
committed pair and asserts three things about what it printed: that the
exit code is 1, that standard output names the change kind the recolour
produces, and that it names a rectangle. This is success criterion 1's
actual claim, which is not that an SVG pair compares but that it compares
at the same quality a raster pair does: a named kind and a bounding box,
never a bare pixel count. Assert the kind and the rectangle separately, so
a failure says which half is missing. Take the expected kind from what the
binary prints for the recoloured raster pair under
`tests/golden/rule-01/`, rather than from a string typed from memory, and
record in the summary the line the SVG run actually printed.

`an_svg_file_with_no_extension_still_dispatches_to_svg_source` copies
`base.svg` into a temporary file with no extension, runs the binary
through `Command::new(env!("CARGO_BIN_EXE_chrys"))` against a second copy
of `candidate.svg` with no extension, and asserts the run produced a
change verdict rather than a decode failure. An extension-driven dispatch
cannot pass this.
`no_committed_fixture_is_taken_from_the_adapter_it_already_used` asserts
`looks_like_svg` is false for every committed still and animated fixture:
the PNG, JPEG, WebP and TIFF pairs under `tests/golden/formats/`, and the
GIF, APNG and animated WebP bases. A sniff that says yes to everything
passes a one-file test and fails this one.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SVG file to adapter | An XML document crosses into `chrys-source-svg`. Its declared width and height, its byte length, its element nesting and every font-family name in it are untrusted. |
| host machine to rendering | A font database is an input the machine supplies. DET-05 says that input must not exist, so the boundary is closed at compile time rather than policed at run time. |
| file content to dispatch | `named_frames_for` decides which adapter opens a file. A wrong decision sends bytes to a parser that was never meant to read them. |
| adapter to engine | Only `Frame` values cross. The engine sees no document, no element and no font. |
