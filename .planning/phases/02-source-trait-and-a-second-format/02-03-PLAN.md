**Crate.** Create `crates/chrys-source-animation`, picked up by the existing
`crates/*` member glob. It declares `#![forbid(unsafe_code)]` and
`[lints] workspace = true`. It depends on `chrys-source` (path), `thiserror`
(workspace) and `image` with `features = ["gif", "png", "webp"]`. Only `gif`

`[dependencies]`, because this crate reuses no code from it and a production
edge would be a dependency this crate does not need.

**Limits.** Define `AnimationLimits { max_width: u32, max_height: u32,
max_alloc: u64, max_frames: usize, max_total_pixels: usize }`. The first
three default to the same numbers `DecodeLimits::default()` uses; the last
two default to the same 512 and 134_217_728 `SequenceLimits` uses. Give the
type a `to_image_limits()` that builds an `image::Limits` exactly as
`DecodeLimits::to_image_limits` does, and apply it to every decoder this
crate constructs, before any frame is pulled. Add a unit test asserting that
the three shared numbers equal `chrys_source_raster::DecodeLimits::default()`'s,
so a later change to one and not the other is a red test rather than a
silent divergence. Measure the claim, do not restate it.

**Sniff.** Create `src/sniff.rs` with
`pub fn is_animation(path: &Path) -> Result<bool, AnimationError>`. It
guesses the format from the file's content, never from its extension, the
same rule `decode_guarded` already follows. A GIF is an animation for this
adapter's purposes. A PNG is one when `image::codecs::png::PngDecoder::is_apng()`
returns true. A WebP is one when `image::codecs::webp::WebPDecoder::has_animation()`
returns true. Anything else is false. Keep every format branch inside this
one function: the CLI asks one question and gets one answer, and a chain of
format-specific branches sprinkled through the CLI's comparison logic is the
per-thing special case this project forbids.

**Adapter.** In `src/lib.rs`, define `AnimationSource` holding an
`AnimationLimits`, with `new()`, `with_limits(..)` and `Default`. Define
`AnimationError` with `thiserror`, carrying at least: the path could not be
read; the file is not an animation this crate decodes; a frame failed to
decode, naming the index; the frame count exceeds `max_frames`; and the
cumulative pixel count exceeds `max_total_pixels`. Implement
`Source for AnimationSource`. Build the format-appropriate decoder, apply the
limits to it, then call `AnimationDecoder::into_frames()` and, for each
`image::Frame` it yields, take `frame.into_buffer()`, read its
`dimensions()`, and build a `chrys_source::Frame` from `into_raw()` with a
sequential `index` and an empty `hints`. Count frames and accumulate pixels
as you go, and stop with the matching error the moment either limit is
crossed; `into_frames()` is a lazy iterator, so a limit checked as frames
arrive is a limit that works on a file declaring a million of them. Discard
`image::Frame::delay()`. This phase pairs by index, and REQUIREMENTS.md
reserves timestamp pairing for video in SRC-06; a duration field added here
would preempt a design that belongs to phase 7.

Write no compositing code. All three decoders resolve their own format's
disposal and blend rules internally and hand back a full-canvas RGBA8 buffer,
which `02-RESEARCH.md` Q1 confirms by reading each decoder's source. A
hand-rolled canvas accumulator in this crate would be new, untested code
solving a solved problem.

This is the one piece of this phase that no crate can do for you, and it is
therefore the one piece that must not be trusted until it is measured.
`image-webp` decodes an animated WebP but encodes only a lossless still
image, so the fixture is built by encoding each frame with the existing
encoder and wrapping the set in a container written by hand.

Write the assembler in
`crates/chrys-source-animation/examples/make-fixtures.rs`, over the same five
frames Tasks 1 and 2 already build. For each frame, call
`image::codecs::webp::WebPEncoder::new_lossless(..).encode(buf, width, height, color_type)`
and extract the `VP8L` chunk payload from the single-image WebP file it
produces. Then assemble a `RIFF`/`WEBP` container holding a `VP8X` header
with the animation bit set, one `ANIM` chunk carrying the background colour
and the loop count, and one `ANMF` chunk per frame. Take the field layout
from Google's WebP container specification, quoted in `02-RESEARCH.md` Q9,
and mind the two fields that are stored differently from how they read: the
frame X and Y offsets are stored as the offset divided by two, and the frame
width and height are stored as the value minus one. Getting either backwards
produces a file some readers tolerate and others reject, which is the failure
mode Pitfall 3 names.

Every frame is lossless, on purpose. Phase 1's six runners proved a lossless
WebP path bit-exact; they never exercised a lossy WebP decode at all. A lossy
animated frame would be new, unproven determinism surface, and there is no
pure-Rust encoder to build one with in any case. Both findings point the same
way, so this fixture is lossless only, and the lossy case stays an open
question rather than an assumed pass. Say that in the generator's own header
comment, so the next reader does not extend the proof past what was measured.

Gate the file on its own round-trip check, in the same commit that creates
it. Inside the generator, immediately after writing each `.webp` file and
before the generator exits, read the file back through
`image::codecs::webp::WebPDecoder`, call `into_frames()`, and assert the
frame count and every frame's pixel buffer equal what was fed in. A mismatch
aborts the generator with a message naming the frame index, so a wrong
container field never reaches `tests/golden/`. Add the same check as a test,
`webp_anim`, in `crates/chrys-source-animation/tests/animation.rs`, so the
committed file is re-verified on every test run and not only at generation
time. Add the sniff assertions: `is_animation` is true for the new fixture
and false for `tests/golden/formats/webp/base.webp`, the still WebP phase 1
committed.

Add the same cross-format agreement assertion Task 2 introduced: frame 0 of
the animated WebP fixture holds the same pixel buffer as frame 0 of the GIF
fixture. All three formats are lossless here and all three were built from
one set of frames, so any disagreement is a container or compositing fault
and not a rounding difference.
