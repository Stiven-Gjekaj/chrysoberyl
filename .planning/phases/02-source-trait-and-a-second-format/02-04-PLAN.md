Prove the phase's headline claim, and extend the determinism matrix to the
fixtures this phase added.

file in the comparison engine. Plan 02-03 was written to satisfy that. This
plan measures it, and first proves the measurement can fail, because phase 1
already learned that a guard nobody has watched go red reports green forever.

demonstration that cannot fail demonstrates nothing. SRC-02 and SRC-03 need
their new fixtures carried onto the six runners, or their determinism is
untested at the one boundary this project cares about.

02-03's commit range, and a digest job that covers every fixture this phase
committed.

  <action>
Write `scripts/engine-boundary-drill.sh` as a sibling of
`scripts/determinism-drill.sh`, not as an addition to it. That script drills
the three determinism guards phase 1 shipped; this one drills a wave-boundary
claim, which is a different kind of property, and folding it in would give one
script two reasons to change.

Follow the existing script's shape exactly, because it is already correct and
a reader who knows one should recognise the other: `set -u`, resolve the
repository root from `$0`, refuse to run when `git status --porcelain` prints
anything and say why, create a disposable worktree with `mktemp -d` and
`git worktree add --detach --quiet`, remove it on every exit path through a
`cleanup` function installed with `trap cleanup EXIT INT TERM`, count passes
and failures, print one `drill ok:` or `DRILL FAILED:` line per drill, and
exit non-zero when any drill did not behave as expected. Never edit the real
working tree.

The check the script drills is one command:

```sh
git diff --name-only <first-commit>^..<last-commit> -- crates/chrys-core/
```

Empty output is the pass condition. Any output is a failure, and each line is
the path of a file under the engine directory that the range changed.

Drill one, the planted defect. Inside the worktree, append a harmless comment
line to an engine source file and commit that change together with a change
to a file in the animation adapter crate, so the planted commit looks like a
real wave commit that happens to have reached across the boundary. Run the
check over that commit's own range. Assert two things, not one: that the
check produced output, and that the output names the exact engine file that
was planted. A check that goes red for the wrong reason is not better than one
that stays green. Print the check's output when the drill fails, the way the
existing script prints a failing guard's output.

Drill two, the clean range. Run the same check over the real commit range of
plan 02-03, read from `02-03-SUMMARY.md` and passed to the script as two
arguments so the script is re-runnable against any range and does not hold a
hash of its own. Assert the output is empty. Print the range and the empty
result, so the summary can quote it.

Take the two commit hashes as `$1` and `$2`, with a usage message when they
are missing that names what they are: the first and last commit of the wave
whose boundary is being checked.

Run the script and record its complete output verbatim in the summary. Both
drills must behave as expected before this task is done.

Carry this phase's fixtures onto the six runners. A fixture that only ever
decodes on the machine that made it proves nothing about portability, which
is the one claim this project says out loud.

Extend the digest step of the `digest` job so it runs `compare --hash-only`
once per fixture pair and writes one `digest.txt` per runner holding all of
them. Keep the existing `tests/golden/pair-01` pair first and its four lines
unchanged and unprefixed, so the file a reader already knows still opens the
same way. After it, append one section per new pair, each introduced by a
line naming the fixture directory, then that pair's own report. The pairs to
add are `tests/golden/sequence-01/{base,candidate}`,
`tests/golden/formats/gif/{base,candidate}.gif`,
`tests/golden/formats/apng/{base,candidate}.png` and
`tests/golden/formats/webp-anim/{base,candidate}.webp`. Use `bash` as the
step shell, as the existing steps already do, so one script runs on all three
operating systems.

Replace the `agree` job's comparison logic. Today it reads four fixed lines by
number and compares them field by field, which cannot survive a report whose
length depends on the fixture set. Compare each runner's whole `digest.txt`
against the first runner's, byte for byte, and on a disagreement print the
`diff` for every runner that differs, keeping the existing message that a red
`agree` job is a portability bug in the comparison path and a release blocker
rather than a flaky test to retry. Byte comparison is both simpler and
stronger than the loop it replaces: it cannot miss a line the loop was not
told about.

Change nothing else about this workflow. The triggers stay `push` and
`pull_request`, `pull_request_target` appears nowhere, `permissions` stays
`contents: read`, every action stays pinned to its 40-character commit hash,
and no toolchain-install action is added, because the runner's own rustup
reading `rust-toolchain.toml` is a determinism input this project depends on.
Phase 1 recorded those as decisions; this task inherits them and does not
revisit them.

Prove the new comparison can fail before you trust it. Locally, produce two
copies of a runner's `digest.txt`, change one character in one digest of one
copy, run the same comparison the `agree` job runs over the two files, and
confirm it exits non-zero and its output names the line that differs. Record
the command and its output verbatim in the summary. This is the same
discipline the boundary drill applies to the boundary check, applied to the
comparison logic this task rewrites.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| commit history to boundary check | The check reads a commit range supplied by a person. A wrong range checks the wrong thing and still prints nothing. |
| repository to CI runner | The workflow runs on six hosted runners against a checkout of this repository. |
| runner artifacts to the agree job | Six digest reports are uploaded and compared. The comparison decides whether the portability claim holds. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-13 | Repudiation | the engine-boundary check | high | mitigate | An empty result is the pass condition, and an empty result is also what a wrong range, a typo in the path filter or a silently failing command produces. Drill one plants a defect and asserts both that the check produced output and that the output names the planted file, so the check is proven able to fail before its silence is read as evidence. |
| T-02-14 | Tampering | the commit range the check reads | medium | mitigate | The range comes from `02-03-SUMMARY.md`, recorded by the wave that produced it, and is passed to the script as two arguments rather than embedded in it. The script prints the range it checked, so the summary records which commits were actually measured rather than which were intended. |
| T-02-15 | Repudiation | the `agree` job's comparison | high | mitigate | The comparison is rewritten in this task, so its previous evidence does not transfer. A local run over two files differing in one character proves the new logic goes red and names the line, and that run is recorded verbatim. |
| T-02-16 | Elevation of Privilege | the CI workflow | medium | mitigate | The workflow keeps `push` and `pull_request` triggers with no `pull_request_target`, keeps `permissions: contents: read`, and keeps every action pinned to a 40-character commit hash. Phase 1 established these and this task changes none of them; an acceptance criterion checks each one. |
