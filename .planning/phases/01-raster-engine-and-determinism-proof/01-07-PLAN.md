**As a** person who reviews visual changes, **I want to** compare two raster
images and read a structural verdict, **so that** the verdict is byte-identical
on every operating system and CPU architecture.

<!-- planner-discipline-allow: empfindung -->
<!-- planner-discipline-allow: delta_e -->

<objective>
Turn a residual field into a verdict a person can read. This plan groups the
changed pixels, drops the ones that are only antialiasing, and names what each
remaining group is.

Purpose: this is the differentiator the project research says no surveyed
competitor offers. Every other tool reports a score or a count. Chrysoberyl
reports that a region moved by twelve pixels, or that a region changed colour
from one value to another. CORE-01 exists to stop this project from becoming a
better pixel counter.

Purpose, second half: CORE-03 is where the phase's transcendental risk lands.
Lab conversion needs a cube root whatever colour-difference formula sits on top
of it, and Rust's own documentation lists that function as varying by platform,
by Rust version, and even between two calls inside one execution. The `palette`
crate's `libm` feature routes it through pure Rust instead. That feature is not
an option here; it is the requirement.

Output: labelled regions with bounding boxes, an antialiasing filter with its
blind spots written down, a colour difference with both colours, and a named
kind for every region.
</objective>

    - `is_antialiasing` returns false for a pixel in a solid-colour area, because
      more than two of its eight neighbours have a zero brightness delta.
    - `is_antialiasing` returns true for a pixel on a smooth one-pixel-wide
      brightness ramp that both frames share.
    - `is_antialiasing` returns false for a pixel at the centre of a solid block
      that changed colour, because neither endpoint of its local ramp looks like
      a gradient.
    - `suppress_antialiasing` on a pair that differs only along the edge of a
      diagonal line returns an empty region list.
    - `suppress_antialiasing` on a pair with a real recoloured block keeps that
      block's region.
    - The suppression runs before labelling, so an antialiasing pixel never joins
      a region.
  </behavior>
  <action>
Add the antialiasing filter and be honest about what it cannot do.

Write `crates/chrys-core/src/classify/antialias.rs` with
`pub fn is_antialiasing(base: &Frame, candidate: &Frame, x: u32, y: u32) -> bool`
and
`pub fn suppress_antialiasing(residual: &mut ResidualField, base: &Frame, candidate: &Frame)`.

Implement the rule the research quotes from pixelmatch, in Rust. For the pixel
under test, walk its eight neighbours in the baseline and track the smallest and
the largest brightness delta and the neighbour position at each extreme. Return
false immediately when more than two neighbours have a zero delta, because that
is a solid-colour area and not an edge. When a genuine smallest and largest pair
exists, test whether the pixel at each of those two extreme positions has more
than two neighbours of its own with an identical value, in both the baseline and
the candidate. Only when both endpoints of the local brightness ramp look like
part of a smooth gradient in both frames is the pixel classified as
antialiasing. Hold the neighbour count threshold as a named constant.

Write the rule's provenance and its limits in a doc comment at the top of the
module, in four sentences. First, this is pixelmatch's own heuristic, not an
implementation of Yee 2004, which handles antialiasing implicitly through a
Laplacian pyramid and a contrast sensitivity function and has no explicit
pixel rule at all. Second, a thin single-pixel feature such as a hairline or a
small dot can fail the neighbour-count test even when it is genuinely just
antialiased, because its neighbourhood has too few pixels sharing its value.
Third, a real small change that happens to produce a smooth local gradient in
both frames will be classified as antialiasing and suppressed. Fourth, both
limits are known and accepted for this phase, and a future perceptual metric is
the fix, not a wider threshold.

`suppress_antialiasing` zeroes every residual sample whose pixel
`is_antialiasing` accepts, before `label_regions` runs. Call it from
`label_regions`'s caller, not from inside `label_regions`, so the two stages
stay separately testable.

Add the tests named in the behaviour block to
`crates/chrys-core/tests/classify.rs`. Build the diagonal-line case inside the
test by rendering the same diagonal at two subpixel positions with integer
coverage arithmetic, so the difference is genuinely edge-only.

Write `crates/chrys-core/src/classify/colour.rs` with
`pub fn colour_delta(base: [u8; 4], candidate: [u8; 4]) -> ColourDelta`. Convert
each RGBA value to the crate's sRGB type, convert to Lab, and take the Euclidean
distance between them. Record in a doc comment why this formula and not the 2000
formula: the 2000 formula needs an arc tangent, a sine, a cosine and a power
function on top of the cube root every Lab conversion already needs, while the
Euclidean distance needs only a square root, which Rust's precision
documentation states is guaranteed not to change. Record that the richer formula
is the intended upgrade once the six-runner matrix is green and a second data
point exists, and that the upgrade also routes through this crate's pure-Rust
feature.

Write `crates/chrys-core/src/classify/kind.rs` with
`pub fn classify_kind(region: &LabelledRegion, base: &Frame, candidate: &Frame, blocks: &[BlockOffset]) -> (ChangeKind, Option<(i32, i32)>, Option<ColourDelta>)`.
Compute the frame background once, as the modal RGBA value over the baseline,
using an integer histogram. Then apply an ordered decision list, in this order,
with each threshold a named constant carrying a doc comment:

One, the region is background in the baseline and not in the candidate, so it is
`Added`. Two, the reverse, so it is `Removed`. Three, both frames hold content
but the non-background pixel count inside the bounding box differs by more than
the named fraction while the majority block offset is zero, so it is `Resized`.
Four, the majority block offset over the blocks intersecting the bounding box is
non-zero, so it is `Moved`, and that offset is the reported offset in pixels.
Five, the fall-through is `Recoloured`, and its colour delta is the difference
between the mean colour of the region in each frame.

Write the fall-through choice in a doc comment with its reason: a region that
reached the residual and is none of the first four differs in colour by
definition, so `Recoloured` is the honest default rather than an unnamed
category. Define "region is background" as at least the named fraction of its
pixels equal to the modal value, and take the majority block offset by count
with a tie broken toward the smaller magnitude, matching the block match
convention.

Extend the `Display` implementation in `crates/chrys-core/src/verdict.rs` so a
region line names the kind, gives the bounding box, gives the offset in pixels
when the kind is `Moved`, and gives the difference value and both colours when a
colour delta is present. A pixel count may appear on the line, but never as the
only content of the line.

Change `compare` in `crates/chrys-core/src/lib.rs` to call `classify_kind` per
