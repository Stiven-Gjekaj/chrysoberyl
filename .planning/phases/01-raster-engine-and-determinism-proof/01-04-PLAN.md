**As a** person who reviews visual changes, **I want to** compare two raster
images and read a structural verdict, **so that** the verdict is byte-identical
on every operating system and CPU architecture.

<objective>
Register a pair globally. This plan finds the translation between two
near-identical frames and reports it in pixels, and it does so on one arithmetic
path that every machine takes.

Purpose: this is the plan where the phase's two named determinism traps live.
The first is the FFT planner: the default planner in `rustfft` detects AVX, SSE
and NEON at run time and picks a different algorithm per machine, so two
machines can silently take different arithmetic through the same call. The
second is the window function: the raised cosine that feeds the transform is the
sharpest transcendental risk in the whole phase, because the standard library
documents its cosine as varying by platform and by Rust version. Both are closed
here, with a test each, not with a comment.

Output: a coarse global offset in pixels, refined to subpixel accuracy, on a
fixed working resolution, with a fixed transform digest guarding the arithmetic
path.
</objective>

## Locked decisions honoured

| Decision (PROJECT.md) | How this plan honours it |
|---|---|
| A baseline is portable (Core Value) | One FFT code path on every CPU. One cosine implementation on every platform. |
| The engine assumes near-identical pairs | Phase correlation plus block matching is the whole registration scope. No feature matching, no homography, no optical flow. |
| No pixel entering a comparison comes from a GPU | Every transform in this plan runs on the CPU. |

## Plan assumptions to settle at implementation time

Both come from 01-RESEARCH.md. Neither is hardcoded here.

1. **The `realfft` question.** 01-RESEARCH.md Open Question 2 asks whether
   `realfft` 3.5.0 lets a caller supply a scalar `rustfft` planner, or always
   builds its own. Check the 3.5.0 documentation before you add the dependency.
   If injection is available, use `realfft` and halve the transform work. If it
   is not, drop `realfft` entirely and call the scalar planner directly on
   complex input. Record which branch you took in the SUMMARY. Do not add
   `realfft` to `Cargo.toml` speculatively.
2. **Auto-vectorization.** The scalar planner removes the library's own run-time
   dispatch. The compiler's own vectorizer still runs. It does not reassociate
   floating-point sums without an explicit fast-math flag, which this project
   never sets, so per-element vectorization is expected to stay bit-identical.
   That is reasoning, not a measurement. The transform digest test in Task 1 is
   the local measurement, and the six-runner matrix from plan 01-03 is the full
   one.

Write `src/register/luma.rs` with
`pub fn to_luma_downsampled(frame: &Frame) -> Vec<u8>`. It converts each RGBA8
pixel to a single luma byte with integer weights, using the fixed-point form
that multiplies red by 77, green by 150 and blue by 29 and shifts the sum right
by 8, and it box-averages into a `WORKING_RESOLUTION` by `WORKING_RESOLUTION`
grid with integer division. There is no floating-point arithmetic anywhere in
this file, and no interpolation kernel. Document that the integer path is chosen
because it removes a whole class of rounding divergence before the transform
ever runs.

Write `src/register/window.rs` with three public items.
`pub const WORKING_RESOLUTION: usize = 512`, with a doc comment stating that the
value is a determinism input and not a performance knob: it fixes the size of
the coefficient table, and changing it invalidates every committed digest.
`pub fn hann_table(n: usize) -> Vec<f32>` builds the raised-cosine coefficients
once, computing each coefficient in `f64` through the pure-Rust `libm` crate's
cosine function and casting the result to `f32`. Never call the standard
library's cosine method here or anywhere else in the register stage: Rust's own
precision documentation lists that method as having unspecified precision that
varies by platform, by Rust version, and even between two calls in one
execution. `pub fn plan_scalar_fft(len: usize, direction: FftDirection) -> Arc<dyn Fft<f32>>`
constructs `rustfft`'s scalar planner and returns the plan. The scalar planner is
the only planner this crate ever constructs. Put a doc comment on
`plan_scalar_fft` naming the reason: the auto-dispatching planner detects AVX,
SSE and NEON at run time and switches algorithm, so two machines running the
same build can take different arithmetic through the same call.

Write `src/register/phase_correlation.rs` with `CoarseOffset { dx: i32, dy: i32 }`,
`CorrelationSurface` holding the inverse-transform magnitudes and the working
resolution, and
`pub fn phase_correlate(base: &Frame, candidate: &Frame) -> Result<(CoarseOffset, CorrelationSurface), CompareError>`.
The steps, in order: downsample both frames through `to_luma_downsampled`;
multiply each row and each column by the cached Hann table so edge effects do
not streak the peak; run the forward 2D transform as a row pass followed by a
column pass, every 1D plan coming from `plan_scalar_fft`; form the cross-power
spectrum by multiplying the baseline spectrum by the conjugate of the candidate
spectrum; normalize each bin by its own magnitude, computed with the square-root
method, which Rust's precision documentation states is guaranteed not to change,
and set a bin to zero when its magnitude is zero rather than dividing; run the
inverse 2D transform the same way; and take the largest magnitude in the
surface, breaking a tie by the lowest linear index so the result never depends
on iteration order. Convert the peak index into a signed offset by treating
indices above half the working resolution as negative, then scale both axes back
to full-frame pixels by the downsample ratio.

Cache the Hann table with a `OnceLock` at the working resolution so it is
computed once per process, never per pixel and never per call.

Write `crates/chrys-core/tests/register.rs` with the tests named in the

Add the subpixel refinement step the architecture research names.

Write `src/register/subpixel.rs` with
`pub fn refine_peak(surface: &CorrelationSurface, coarse: CoarseOffset, upsample_factor: u32) -> RefinedOffset`,
where `RefinedOffset` carries the whole-pixel offset and an `f32` fractional
part per axis. Implement the upsampled discrete Fourier transform of
Guizar-Sicairos, Thurman and Fienup: build the small upsampled neighbourhood
around the coarse peak by a direct matrix-multiply transform over that
neighbourhood only, never by upsampling the whole surface, and take the maximum
of the upsampled neighbourhood as the refined peak. Use an upsample factor of
100, held as a named constant beside the function with a doc comment stating it
fixes the refinement resolution at one hundredth of a pixel.

Every complex exponential this step needs comes from the pure-Rust `libm`
crate's sine and cosine functions, for the same reason the window table does.
Precompute the twiddle values for the neighbourhood once per call into a small
table, so the transcendental count is a function of the neighbourhood size and
not of the surface size. Break a tie in the upsampled maximum by the lowest
linear index, matching the coarse stage's convention.

Extend `CoarseOffset`'s call site in `phase_correlation.rs` so `phase_correlate`
returns the refined offset alongside the coarse one. Keep the whole-pixel field
as the value CORE-02 reports, and document that the fractional part exists for
the block-match stage in plan 01-06 and for a future warp, not for the printed
verdict.

Add the tests named in the behaviour block to
`crates/chrys-core/tests/register.rs`. Build the half-pixel case by averaging
two adjacent columns of a synthetic image, which is a half-pixel shift by
construction and needs no resampling library.
