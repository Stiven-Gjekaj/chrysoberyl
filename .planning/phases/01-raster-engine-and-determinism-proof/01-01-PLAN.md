**As a** person who reviews visual changes, **I want to** compare two raster
images and read a structural verdict, **so that** the verdict is byte-identical
on every operating system and CPU architecture.

*(Derived from the ROADMAP Phase 1 Goal line. It is a reformat of that
sentence, not a new story.)*

CONTEXT.md for this phase, so PROJECT.md is the source of locked decisions.

| Decision (PROJECT.md) | How this plan honours it |
|---|---|
| No pixel entering a comparison comes from a GPU | No GPU crate is added to any `Cargo.toml`. `chrys-core` depends on no graphics crate. |
| The engine assumes near-identical pairs | `compare` refuses a dimension mismatch instead of scaling or cropping. |
| One engine, one meaning of "changed" | `Verdict` lives in `chrys-core` only. No adapter produces a verdict. |
| Core crate and CLI first, window second | This plan creates no window and no GPU code. |
| The core is MIT and pure Rust | Only pure-Rust crates are added. |
| No per-thing special case, ever (AGENTS.md, PROJECT.md) | `chrys-core` has no format crate in its `Cargo.toml`, so a format branch cannot compile there. |

`rustfft = "=6.4.1"`, `realfft = "=3.5.0"`, `imageproc = "=0.27.0"`,
`palette = { version = "=0.7.7", default-features = false, features = ["libm"] }`,
`libm = "=0.2.16"`, `sha2 = "=0.11.0"`, `thiserror = "=2.0.20"`,
`anyhow = "=1.0.104"`, `clap = { version = "=4.6.6", features = ["derive"] }`.
Re-run `cargo search <name> --limit 1` for each before you pin, because
01-RESEARCH.md says its own numbers are 30-day perishable. If a version has
moved, pin the version the registry reports today and record the change in the
SUMMARY. Only `image`, `palette` and `clap` carry feature lists here; the
remaining crates take no features. Add `[workspace.lints.rust]` with
`rust_2018_idioms = "warn"` and `[workspace.lints.clippy]` with
`all = "warn"`; each member crate opts in with `[lints] workspace = true`.

Write `rust-toolchain.toml` pinning `channel = "1.97.1"`,
`profile = "minimal"`, `components = ["rustfmt", "clippy"]`. Put a comment above
it that says the pin is a determinism input, not a convenience: Rust's own
precision documentation states that `sin`, `cos`, `cbrt`, `powf`, `exp`, `ln`
and `atan2` vary by platform and by Rust version.

Edit `.gitignore` to ignore `/target` and `**/*.rs.bk`. Do not ignore
`Cargo.lock`; the lock file is committed, because a transitive version bump is a

Step 2, `crates/chrys-source`. This crate depends on nothing outside the
standard library. Define `Frame` with public fields `pixels: Vec<u8>` (RGBA8,
straight alpha, row major, no row padding), `width: u32`, `height: u32`,
`index: usize` and `hints: Vec<RegionHint>`. Define `RegionHint` with `name`,
`x`, `y`, `width`, `height`. Define `trait Source` with an associated
`type Error` and one method `load(&self, path: &Path) -> Result<Vec<Frame>, Self::Error>`.
Add `Frame::pixel_count`, `Frame::rgba8` returning a slice, and
`Frame::same_shape_as` returning a bool. Document on `Frame` that the buffer is
straight alpha and that no `image` crate filter may run on it without a
conversion first. Put `#![forbid(unsafe_code)]` at the top of the file.

Step 3, `crates/chrys-source-raster`. It depends on `chrys-source`, `image` and
`thiserror` from the workspace table, with `image` features set to `["png"]`
only in this plan. It never depends on `chrys-core`. Define `DecodeLimits` with
`max_width`, `max_height` and `max_alloc`, and a `Default` of 16384, 16384 and
512 MiB. Define `RasterSource` holding a `DecodeLimits`, with `new()` and
`with_limits()`. Implement `Source for RasterSource`: open the path with
`image::ImageReader`, call `set_limits` with an `image::Limits` built from
`DecodeLimits` before any pixel buffer is allocated, decode, convert to RGBA8,
and return a one-element `Vec<Frame>` with `index` 0 and empty `hints`. Define
`RasterError` with `thiserror`, carrying `Io`, `Decode`, `TooLarge { width,
height, limit }` and `Unsupported`. Every decode call site in this crate sets
limits; there is no unguarded decode path. Put `#![forbid(unsafe_code)]` at the
top.

Step 4, `crates/chrys-core`. It depends on `thiserror` only in this plan, and on
`chrys-source` for the `Frame` type. It depends on no format crate and on no
graphics crate, and that stays true for the whole project. Write
`src/verdict.rs` defining `BoundingBox { x, y, width, height }`,
`ColourDelta { delta_e: f32, base: [u8; 4], candidate: [u8; 4] }`,
`ChangeKind` with the five variants `Moved`, `Added`, `Removed`, `Recoloured`
and `Resized`, `Region { kind, bbox, offset_px: Option<(i32, i32)>, colour_delta:
Option<ColourDelta> }`, `RefusalReason` with `DimensionMismatch { base: (u32,
u32), candidate: (u32, u32) }`, and `Verdict` with `Identical`,
`Changed { regions: Vec<Region> }` and `Refused { reason: RefusalReason }`. Give
`Verdict` an `is_change()` method and a `Display` implementation that prints one
line per region naming the kind, the bounding box and, when present, the colour
delta and both colours. `Display` never prints a bare pixel count on its own;
a count may appear only beside a named kind.

Write `src/lib.rs` with `pub mod verdict;` and
`pub fn compare(base: &Frame, candidate: &Frame) -> Result<Verdict, CompareError>`.
The tracer implementation is real for the one path it serves: return `Refused`
with `DimensionMismatch` when the shapes differ; walk both buffers once and
collect the bounding box of every pixel whose RGBA bytes differ; return
`Identical` when no pixel differs; otherwise return `Changed` with one `Region`
of kind `Recoloured`, that bounding box, `offset_px` of `None`, and a
`ColourDelta` whose `base` and `candidate` are the RGBA values at the top-left
pixel of the bounding box and whose `delta_e` is the Euclidean distance in
straight RGB, cast to `f32`. Leave a doc comment on `compare` stating that the
single-region bounding box is the degenerate case of connected-component
labelling, which plan 01-07 replaces, and that `delta_e` is a stand-in metric
until plan 01-07 routes it through `palette`. `CompareError` is a `thiserror`
enum with one variant, `EmptyFrame`. Put `#![forbid(unsafe_code)]` at the top.

Step 5, `crates/chrys-cli`. It depends on `chrys-source`, `chrys-source-raster`,
`chrys-core`, `clap` and `anyhow`. Define the binary name `chrys` in
`[[bin]]`. Use a `clap` derive `Parser` with a `compare` subcommand taking two
positional path arguments, `base` and `candidate`. The command loads both paths
with `RasterSource::new()`, takes the first `Frame` of each, calls
`chrys_core::compare`, prints the `Display` form of the verdict to stdout, and
returns an exit code: 0 for `Identical`, 1 for `Changed`, 2 for `Refused`, 3
when a load or compare call returns an error. Print the error to stderr, never
to stdout, so stdout stays parseable. Put `#![forbid(unsafe_code)]` at the top.

Step 6, the fixture pair. Write
`crates/chrys-source-raster/examples/make-fixtures.rs`. It builds two 256 by 256
RGBA8 images in memory. Both have the same background. The baseline draws a
solid rectangle at x 64, y 64, width 96, height 64 in one colour; the candidate
draws the same rectangle in a different colour. Nothing else differs. It writes
`tests/golden/pair-01/base.png` and `tests/golden/pair-01/candidate.png` with
the `image` crate's PNG encoder at its default settings. Add `image` to this
crate's `[dev-dependencies]` with the `png` feature so the example can encode.
Run the example once and commit both PNG files. The generator is committed so a
reader can see how the bytes were made; the PNG files are committed because
every later determinism check must read a real file from disk, not a buffer
built in memory.

Write the unit tests named in the behaviour block beside the code they test, in
the same commit as that code.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| file on disk to decoder | Untrusted bytes cross here. The `image` crate parses attacker-controlled structure. |
| command line to file system | A path argument selects which file the process opens. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Denial of Service | `RasterSource::load` in `crates/chrys-source-raster/src/lib.rs` | high | mitigate | Build `image::Limits` from `DecodeLimits` and call `set_limits` on the reader before any pixel buffer is allocated. This is the named mitigation for the CVE-2023-29408 decompression-bomb class. |
| T-01-02 | Denial of Service | `image::ImageReader` dimension handling | high | mitigate | Limits carry `max_image_width`, `max_image_height` and `max_alloc`, so a crafted header is rejected before allocation, not after. |
| T-01-03 | Tampering | `chrys-core` dependency list | medium | mitigate | `chrys-core` declares no format crate, so untrusted parsing code cannot reach the engine. The boundary is a compile-time fact, not a review rule. |
| T-01-SC | Tampering | cargo installs from crates.io | high | mitigate | Every crate this plan adds carries an `OK` verdict in the Package Legitimacy Audit of 01-RESEARCH.md, with a registry age, a download count and a source repository. No `[ASSUMED]`, `[SUS]` or `[SLOP]` package is installed, so no blocking human checkpoint is required. Versions are pinned with `=` requirements and `Cargo.lock` is committed. |
| T-01-04 | Information Disclosure | CLI error output | low | accept | A decode error names the path the user already typed. Paths go to stderr, never to stdout. |
</threat_model>
