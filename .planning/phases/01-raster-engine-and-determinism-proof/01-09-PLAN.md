**As a** person who reviews visual changes, **I want to** compare two raster
images and read a structural verdict, **so that** the verdict is byte-identical
on every operating system and CPU architecture.

<objective>
Close gap G-01-1. A pair that differs only in the alpha channel is reported
`identical` with exit code 0 today. The engine's own decode digests see the
difference its verdict denies. This plan makes alpha part of the comparison,
from the residual through to the name the report prints.

Purpose: the phase goal says a person gets a structural verdict on two raster
images. For an alpha-only edit the tool does not give a weak verdict; it gives a
wrong one, and it gives it with no signal of doubt. That is the one failure mode
CORE-06 and CORE-07 exist to prevent, and here the refusal path is never even
reached. `Frame` is documented as "RGBA8, straight alpha" everywhere in this
codebase, with no note anywhere that alpha is out of scope, so this is an
oversight and not a stated limit.

Output: an alpha-aware residual, an alpha-aware foreground test, an
antialiasing rule that still suppresses what a person cannot see, a change name
that is correct rather than merely present, a committed fixture pair built by
the committed generator, and a measured account of which committed digests moved
and which did not.
</objective>

## What changes, and what does not

Registration does not change. The block search runs on a luma pyramid, and luma
answers one question: where did content move to. Alpha does not help locate
content, so the search stays as it is. Detection is a different question: did
this pixel change. Alpha answers that one, so detection gains it. Task 1 writes
that separation into a doc comment, so a later reader does not "complete" the
search by hand.

**Commit two, the rule can see an alpha edge.**

`brightness` reads red, green and blue and ignores alpha. An antialiased edge
authored in straight alpha holds one flat colour with a ramping alpha, so
`brightness` sees a flat neighbourhood, counts more than two zero-delta
neighbours, and returns false at once. The rule then suppresses nothing, and the
engine starts reporting invisible edge noise on every such edge. That is the
highest risk this whole plan carries, and it is why a change to
`difference_image` alone is the wrong fix.

Composite the pixel onto a fixed opaque white reference before weighing it, in
exact integer arithmetic. Take the existing weighted luma, red by 77, green by
150, blue by 29, shifted right by 8. Multiply that by the alpha byte, and add
255 times the complement of the alpha byte. The result is an `i32` in the range
0 to 65025, and it is exactly 255 times today's value whenever alpha is 255.
Write no division: the rule only ever compares two of these values for equality
and for order, and a positive constant scale changes neither. Use a plain
multiply and a plain add, never `mul_add`, because the determinism guard treats
a fused multiply-add as a finding that needs an allow-list entry and a subnormal
test case.

Write the reasoning into the function's doc comment, and name the three
properties that make it safe: it is exact integer arithmetic on every platform;
it is monotone in the true composited value, so every ordering the rule reads is
preserved; and it agrees with the old function up to a factor of 255 on a fully
opaque frame, so no existing suppression decision moves. Extend the module doc
comment to say the white reference is pixelmatch's own choice, which this module
already implements, and that a fixed reference is what makes the answer the same
on two machines.

Add two tests to `crates/chrys-core/tests/classify.rs`. Build a frame pair whose
red, green and blue bytes are one flat colour everywhere and whose alpha ramps
across a soft edge, with the ramp shifted by one pixel between the two sides.
Assert the pair produces no labelled region after suppression. Then build a
