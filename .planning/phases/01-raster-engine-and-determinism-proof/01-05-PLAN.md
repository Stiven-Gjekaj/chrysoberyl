**As a** person who reviews visual changes, **I want to** compare two raster
images and read a structural verdict, **so that** the verdict is byte-identical
on every operating system and CPU architecture.

<objective>
Teach the engine to refuse. A tool that gives a confident answer on a pair it
cannot register is worse than a tool that says it cannot answer, because a
person cannot tell the two apart from the output.

Purpose: CORE-06 and CORE-07 are the honesty requirements of this project. The
engine assumes near-identical pairs by decision, so it must detect when that
assumption is false and say so, in the same run, before it spends any work on a
warp or a classification it cannot support.

Output: a peak-confidence metric, a threshold derived from a measured corpus,
and a refusal verdict that names the numbers it refused on.

**The threshold is not chosen here.** 01-RESEARCH.md Open Question 1 records
that no numeric threshold was verified, and Assumptions Log entry A4 records
that a hardcoded constant would make refusal either too strict or too loose. So
Task 1 measures the corpus and Task 2 derives the constant from the measurement.
</objective>

## Locked decisions honoured

| Decision (PROJECT.md) | How this plan honours it |
|---|---|
| The engine assumes near-identical pairs | The assumption is enforced at run time, not documented and hoped for. A pair outside it is refused, not registered by a heavier algorithm. |
| General image registration is out of scope | The answer to an unregisterable pair is a refusal, never a fallback to feature matching or optical flow. |
| One engine, one meaning of "changed" | A refusal is a `Verdict` variant, so no caller can mistake it for a pass or for a change. |

    - The noise floor excludes a small neighbourhood around the peak, so a sharp
      peak does not raise its own floor.
    - `assess_peak` returns a ratio of zero, not a non-finite value, when the

    - Every pair in the `should-register` corpus scores a higher ratio than

    - The lowest `should-register` ratio and the highest `should-refuse` ratio

  <action>
Build the metric and the corpus that calibrates it, in one commit group.

Write `crates/chrys-core/src/register/confidence.rs` with
`pub struct PeakConfidence { pub peak: f32, pub floor: f32, pub ratio: f32 }`
and
`pub fn assess_peak(surface: &CorrelationSurface, peak_index: usize) -> PeakConfidence`.
The peak is the magnitude at `peak_index`. The floor is the mean magnitude over
every sample outside a square exclusion window centred on the peak, with the
window side held as a named constant beside the function. The ratio is the peak
divided by the floor, and is zero when the floor is zero. Sum the floor in a
fixed index order so the result never depends on iteration order, and document
that choice: a reordered floating-point sum is a different number, and this
number reaches a boolean that decides a verdict. Cite Kuglin and Hines, and
Reddy and Chatterji, in a doc comment as the source of peak sharpness as the
registration confidence signal.

Extend `crates/chrys-source-raster/examples/make-fixtures.rs` to write a
calibration corpus into `tests/golden/refuse-01/`, in two subdirectories.
`should-register/` holds at least four pairs a person would call near-identical:
an identical pair, a pair shifted by a few pixels, a pair with one small
recoloured rectangle, and a pair with one small element added. `should-refuse/`
holds at least four pairs a person would call unrelated: two images built from
different shape sets, a pair where the candidate is the baseline with its
content mirrored, a pair where the candidate is uniform noise from a fixed seed,
and a pair where the candidate is a solid colour. Every image is generated from
deterministic integer formulas so a reader can reproduce the bytes. Keep the
existing outputs of this generator byte-identical; it must not rewrite
`tests/golden/pair-01/` or `tests/golden/formats/`, because plan 01-03 committed
a digest over the first of those. Run the generator once and commit the corpus.

Write `crates/chrys-core/tests/refusal.rs` with a separation test. It loads every
pair in both corpus directories, runs the correlation and `assess_peak` on each,
collects the ratios, and asserts three things: every `should-register` ratio is
strictly greater than every `should-refuse` ratio; the gap between the lowest of
the first group and the highest of the second is greater than zero; and the two
groups each hold at least four pairs. Print both groups of ratios with their
directory names on failure, so a red test names the pair that broke the
separation instead of only the assertion. Record the measured ratios in the
SUMMARY. Those numbers are the input to Task 2.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| decoded frame to registration decision | Attacker-influenced content decides whether a pair registers, so a crafted pair could try to force one branch. |
| corpus file to threshold | A file in the repository sets the number that decides every refusal. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-15 | Spoofing | a crafted pair engineered to score above the threshold | medium | accept | The refusal gate protects the engine's own honesty, not a security boundary. A pair that registers still produces a verdict a person reviews. Recorded as accepted rather than forced into a control that would not help. |
| T-01-16 | Tampering | `REFUSAL_THRESHOLD` edited to silence a failing case | medium | mitigate | The constant's doc comment records the two measured bounds and the midpoint rule, and the separation test re-derives them from the committed corpus on every run, so an edit that is not supported by the corpus goes red. |
| T-01-17 | Denial of Service | floor computation over a large correlation surface | low | mitigate | The surface is always `WORKING_RESOLUTION` squared, fixed by plan 01-04, so the floor cost does not scale with input size. |
| T-01-SC | Tampering | cargo installs from crates.io | high | mitigate | This plan adds no crate. The Package Legitimacy Audit of 01-RESEARCH.md still covers the whole graph, and no `[ASSUMED]`, `[SUS]` or `[SLOP]` package is present, so no blocking human checkpoint is required. |
</threat_model>
