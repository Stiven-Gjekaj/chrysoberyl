**As a** person who reviews visual changes, **I want to** compare two raster
images and read a structural verdict, **so that** the verdict is byte-identical
on every operating system and CPU architecture.

<objective>
Register the pair locally. The global stage removed one translation from the
whole frame. This plan finds what is left: which blocks still disagree, and by
how much each one moved on its own.

Purpose: CORE-02 asks for a translated region and its offset in pixels. A
region, not a frame. That needs a per-block search, and a per-block search needs
a fast rectangle sum, or the cost is a pixel loop for every candidate position.

Output: a warped candidate, an absolute-difference image, a summed-area table, a
coarse-to-fine block match, and the residual field the classify stage reads.

The whole plan is integer arithmetic. That is deliberate. Absolute differences
of bytes and their rectangle sums have exact integer answers, so the block score
cannot depend on a rounding order, on a lane width, or on a summation sequence.
This removes the SIMD reduction-order risk the project research names, by
construction rather than by a build flag.
</objective>

## Locked decisions honoured

| Decision (PROJECT.md) | How this plan honours it |
|---|---|
| The engine assumes near-identical pairs | The block search window is small and centred on the global offset. It is a refinement, not a search over the whole frame. |
| General image registration is out of scope | No feature detector, no descriptor matching, no homography. Block matching only. |
| No pixel entering a comparison comes from a GPU | Every step here is a CPU integer loop. |
| A baseline is portable (Core Value) | Integer arithmetic end to end, so no summation order can move the answer. |

    - `warp_by_offset` with a positive offset moves content by exactly that many

      seed.

    - `IntegralImage::window_sum` over the whole image equals the total.

Write `crates/chrys-core/src/register/warp.rs` with two public functions.
`warp_by_offset(frame: &Frame, dx: i32, dy: i32) -> Vec<u8>` shifts the RGBA8
buffer by whole pixels only. It copies bytes; it never interpolates. Pixels
shifted in from outside the source are filled with a named constant defined
beside the function, documented as the fill value, and the doc comment states
that a vacated edge is filled rather than wrapped, because wrapped content would
invent a change that is not there.
`difference_image(base: &[u8], warped: &[u8]) -> Vec<u8>` returns the per-byte
absolute difference of the two RGBA8 buffers, with the alpha byte of each pixel
set to the largest byte value so the result is a viewable image. Both functions
return an error type only where a length mismatch is possible; otherwise they
take equal-length slices and say so in a debug assertion.

Write `crates/chrys-core/src/register/block_match.rs` with
`pub struct BlockOffset { pub block_x: usize, pub block_y: usize, pub dx: i32, pub dy: i32, pub score: u64 }`,
`pub struct ResidualField { pub width: usize, pub height: usize, pub samples: Vec<u8>, pub blocks: Vec<BlockOffset> }`,
and
`pub fn block_match(base: &Frame, candidate: &Frame, coarse: CoarseOffset) -> Result<ResidualField, CompareError>`.

The steps, in order. Warp the candidate by the coarse offset. Build a small
pyramid by repeated two-by-two integer box reduction, with the number of levels
held as a named constant. At the coarsest level, for each block of a named
constant side, search every whole-pixel offset inside a search window of a named
half-width, scoring each candidate offset by the sum of absolute differences
over the block, read from a summed-area table built once per candidate offset
rather than by a pixel loop per block. Carry each level's winning offset down as
the starting point for the next finer level, and search only a small window
around it there. At the finest level, record the winning offset per block into
`BlockOffset`, and write the absolute difference at the winning offset into the
residual samples for that block's pixels.

Break every tie the same way, and say so in a doc comment: prefer the smaller
offset magnitude, then the lower search index. An untied comparison is where a
platform difference hides.

Build one summed-area table per candidate offset over the whole difference
image, and answer every block's score from it. Do not loop pixel by pixel inside
each block for each candidate; that is the named anti-pattern that summed-area
tables exist to remove.

Cite the x264 motion-estimation practices the architecture research names, in a
doc comment: the median predictor for the starting point, the diamond and
hexagon search shapes, and early termination on a score that cannot be beaten.
Implement the starting-point prediction and the early termination; the search
shape may stay a full window scan at this block size, and record that choice in
the SUMMARY.

Replace the body of `residual_rgba8` in `crates/chrys-core/src/residual.rs` so it
