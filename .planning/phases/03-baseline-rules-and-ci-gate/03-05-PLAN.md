A rule is written against a frame. A comparison happens on a crop. Today
the tool mixes the two, and the mixture reports success on a change nobody
tolerated. Give the whole run one coordinate space, and make it the
frame's.

**Which frame each consumer must see.** A rule author names a region that
exists in the frame, or draws a mask the size of the frame. That is the
universe a rule lives in, so it is the universe every consumer must read.
The crop is an optimisation of what gets compared, not a new set of
coordinates for what gets reported. Three consumers, three answers:

- The pixel comparison reads the CROPPED frames. That is what `--region`
  is for and it does not change.
- The rule engine and the report writer read the UNCROPPED base frame's
  hints and the UNCROPPED base frame's width and height.
- Every rectangle a run reports, on standard output and in the report file,
  is stated in the UNCROPPED frame's coordinates.

**Stop shadowing.** In `run_compare`, keep `base_frames` and
`candidate_frames` bound to the uncropped frames `named_frames_for`
returned. Bind the cropped frames to their own separate names. Do not reuse
either original name for a cropped value anywhere in the function. The
whole defect is one rebinding that made two different things share one
name.

**Produce the crop origin where the hint is read.** Change
`crop_frames_to_region` so it returns each cropped frame paired with that
frame's own crop origin, the hint's `x` and `y`. The origin is made at the
one place the hint is looked up, so it cannot drift from the hint it came
from. This is the same rule T-03-17 already applies to the frame-to-name
pairing. A sequence gets one origin per frame, because a hint can sit at a
different place on each frame. When `--region` is absent, every origin is
(0, 0).

**Translate the verdicts once, unconditionally.** After
`compare_sequence` returns, build a translated copy of every verdict by
adding that frame's crop origin to the `x` and `y` of every `Region`'s
`bbox`. Run this on both paths, with and without the flag, so the flag-less
path and the region path share one code path and no second place exists
where a coordinate space can diverge. With no flag the origin is (0, 0) and
the copy equals the original by value, so standard output stays byte for
byte what it is today, which `cargo test -p chrys-cli --test digest`
proves.

Three details decide whether the translation is right:

- Translate positions. Do not translate a delta. `Region.offset_px` is how
  far content moved, not where it is, so it stays as the engine reported
  it. `bbox.width` and `bbox.height` are sizes and also stay.
- `Verdict::Identical` and `Verdict::Refused` carry no rectangle. Copy them
  through unchanged.
- Add with `checked_add` and fail the run naming both numbers when it
  returns `None`. The sum provably fits, because `crop_to_region` already
  refuses a hint that does not fit the frame, so an overflow here means an
  assumption broke and a person needs to read which. Do not reach for
  `saturating_add`, which would turn a broken assumption into a quiet wrong
  answer.

Every consumer after this point reads the translated verdicts: the rule
outcomes, the report, both output branches, and `verdict_rank`.

`accept` is the operation success criterion 5 names. Today it deletes the
last known good baseline first and writes the replacement afterwards. A
failure between those two points leaves the store holding neither.

**Build the new state beside the old one, then swap.** Rewrite
`write_baseline` so nothing a reader or a later accept can see is touched
until the new state is complete on disk.

Order the work like this:

1. Compute the staging directory as `<root>/.<name>.accept-tmp`. It is a
   sibling of the baseline directory, under the same root, so it sits on
   the same file system and a rename between them is a rename rather than a
   copy.
2. Remove the staging directory if one already exists, then create it
   fresh. A staging directory left behind by an earlier crash holds files
   from a candidate nobody accepted, and reusing it would copy them into
   the new baseline. Clearing it is what stops that.
3. Copy every candidate file into the staging directory. Keep the existing
   rules exactly: regular files only, no recursion into a nested directory,
   same names, byte for byte. That behaviour is T-03-24 and it does not
   change here.
4. Read the manifest, replace this name's entry, sort by name, serialise,
   and write the result to `<root>/MANIFEST.toml.tmp`. Do not remove a
   stale temporary manifest first. `fs::write` truncates a file that
   already exists, so a stale one is fully overwritten and harmless. The
   asymmetry with step 2 is deliberate and the doc comment states it: a
   stale directory can contribute a file, a stale file cannot contribute a
   byte.
5. Only now touch what a reader sees. Rename the existing baseline
   directory aside to `<root>/.<name>.previous-tmp` when it exists, rename
   the staging directory into the baseline path, rename the temporary
   manifest over `MANIFEST.toml`, and then remove the directory that was
   moved aside.

Step 5 is the whole point: the old content is not deleted until the new
content is in place. Every failure in steps 1 through 4 leaves the store
byte for byte as it was.

**State the window that remains, in the doc comment.** Two renames are not
one atomic act. Between them the new baseline directory is in place and
`MANIFEST.toml` still records the old digests. Say so plainly, and say why
it is acceptable: that disagreement is exactly what the CLI's
`verify_baseline_digests` fails on, loudly, naming the baseline and both
digests (T-03-21). The residual window fails closed. Claiming the write is
atomic would be claiming more than the code does, and this phase has
already recorded once what it costs to record a control as working on
weaker evidence than it needs.

On the error path, remove the staging directory if it exists, on a best
effort basis, and return the original error. Do not let a cleanup failure
replace the error that caused it. A person needs to read why the accept
failed, not why the tidying failed.

**Teach the guard the new verb.** `only_the_accept_path_writes_to_the_store`
holds a constant naming the write calls it searches for, and that
constant's own comment says a new way to write must be added to it or the
guard stops covering it. This task adds one: rename. Add it to the
constant. This is the case that comment was written for.

**The durability test.** Add `a_failed_accept_leaves_the_previous_baseline_intact`
to `crates/chrys-baseline/tests/store.rs`. A durability claim proved by
reading the code is not proved, so this test interrupts a real write:

1. Accept a name into a temporary store from a first candidate.
2. Record the state: the bytes of every file under `<root>/<name>/`, and
   the bytes of `MANIFEST.toml`. Record bytes, not lengths and not a count.
   AGENTS.md records that a size is not a state, and this repository has
   already paid once for measuring something near the thing it meant.
3. Create a directory at `<root>/MANIFEST.toml.tmp`. A write to a path that
   is a directory fails on every platform the matrix runs, it needs no
   permission change, and it fails at step 4 of the new order, after every
   candidate file has already been copied. That is the case CR-02 names
   directly: a manifest write that fails once the files are already on
   disk.
4. Accept the same name again from a second candidate whose bytes differ
   from the first, and assert the call returns an error.
5. Assert every recorded byte string is unchanged, and that `resolve` still

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| rule file to tolerance decision | An untrusted TOML document, which in CI can arrive from a fork's pull request, decides which changes the gate forgives. A mask path and a mask size are both values that document chooses. |
| command line flags to verdict | `--region`, `--rule` and `--report` compose. The composition, not any flag alone, decides what the exit code means. |
| candidate to store | An accept replaces the file every later comparison is measured against. A failure partway through decides whether the previous truth survives. |
| mask path to file system | A checked path and an opened path are two resolutions of the same text, and only one of them was checked. |
