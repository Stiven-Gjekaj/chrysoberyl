<objective>
Make a declarative TOML rule file decide whether a change counts, and let
that decision reach the process exit code.

Phase 1 and phase 2 built an engine that names a change. Nothing yet says
which named change a person accepts. This plan adds the file that says so,
and the smallest honest path from that file to a CI gate: a rule scoped to
a named region, a tolerance scoped to a kind of change, and an exit code
that follows both.

Purpose: RULE-01, RULE-02 (its named-region half), RULE-03, RULE-04 (its
type-level half, D-01), RULE-05, CLI-01, and CLI-03's regression guard.

Output: the `chrys-rule` crate, a `--rule <PATH>` flag on `compare`, a
committed `tests/golden/rule-01` fixture, and three exit codes over one
pair that differ only in which rule file was given.
</objective>

**The crate.** Create `crates/chrys-rule`. The workspace `members` glob is
`crates/*`, so no edit to the root `Cargo.toml` is needed. Its dependency
table takes `chrys-core` and `chrys-source` by path, and `toml`, `serde`
with its `derive` feature, and `thiserror` from the workspace table, all
three already pinned and already audited. This crate depends on
`chrys-core`; `chrys-core` never depends on it. That direction is the whole
reason the rule reader lives outside the engine: the engine declares no
`serde` and no `toml` and this phase does not change that.

**The schema.** A rule document holds an array of tables named `rule`.
Deserialize it into a private permissive row type, then apply a second,
explicit validation pass, exactly the two-phase shape
`crates/chrys-source-raster/src/hints.rs` already uses. Wrap every field of
the row in `toml::Spanned<T>`. Research verified, by compiling and running
it against the pinned `toml =1.1.5`, that plain `toml::from_str` populates
those spans with no special deserializer entry point, and that the first
answer from the documentation summary saying otherwise was wrong. The span
is what lets the semantic pass name the exact line of a field `serde`
accepted.

The row's field names are `kind`, `region`, `mask`, `max_offset_px`,
`max_delta_e`, `max_alpha_delta`, `max_area_px` and `allow`. `kind` is a
lowercase string deserialized into a private enum whose variants are
`moved`, `added`, `removed`, `recoloured` and `resized`, one for each
`chrys_core::ChangeKind` variant, through `rename_all = "lowercase"`. Set
`deny_unknown_fields` on the document type and on the row type, so a
misspelled key is a loud failure rather than a rule that silently does
nothing. Every field except `kind` is optional at the `serde` layer,
because the schema's real constraints are the ones `serde` cannot express.

**The validation pass.** Convert each row into a public `Rule` carrying
three things: a `chrys_core::ChangeKind`, a `Scope`, and a `Tolerance`.
`Scope` is an enum with a `Region(String)` variant and a `Mask(PathBuf)`
variant. There is no third variant and no `Option`, so an unscoped rule
cannot be represented at all. That is D-01, taken before planning: an
unscoped rule is refused at parse time, at the type level, not linted. A
row naming neither is refused, and so is a row naming both, because a rule
that answers to two scopes is a rule a reader cannot predict.

`Tolerance` is an enum too, so exactly one tolerance statement per rule is
a type-level fact. This task builds its `Colour { max_delta_e: f32,
max_alpha_delta: u8 }` variant and its `Allow` variant; task 2 adds the
rest. A row carrying no tolerance field is refused: a rule that names a
scope and says nothing about tolerance states nothing.

The `Colour` variant carries two numbers, not one, and the reason is
written down in the engine already. `chrys_core::ColourDelta`'s own doc
comment says `delta_e` covers colour only, that Lab has no axis for alpha,
and that a rule engine reading the type, naming this phase, must read the
alpha difference from the two colours directly or a tolerance meant for
colour would silently swallow an alpha-only change. `max_alpha_delta`
defaults to 0 when the rule file omits it, so the default behaviour is that
a colour tolerance tolerates no alpha movement at all. Phase 1 settled that
alpha is part of what "changed" means; this is that decision reaching the
rule file.

**The size bound.** Add `pub const MAX_RULE_FILE_BYTES: u64 = 1024 * 1024;`
and check `std::fs::metadata(path).len()` against it before reading the
bytes, the same posture and the same limit `hints.rs` already takes for its
sidecar, and for the same reason: a rule file arrives from wherever the
input arrived from, and bounding an allocation after the read is not
bounding it.

**Loading, and where a mask will land.** The public entry point is
`pub fn load_rules(rule_path: &Path) -> Result<LoadedRules, RuleError>`. It
reads the file, parses it, validates it, and returns a `LoadedRules` value.
Put mask resolution behind this same function from the start, even though
this task decodes no mask: plan 03-02 fills `LoadedRules` with the decoded
masks, so a bad mask path fails while the rule file is being loaded, before
any comparison runs, and `evaluate`'s signature never changes. Do not add a
mask parameter to `evaluate`.

**Evaluation.** Create `crates/chrys-rule/src/evaluate.rs` with
`pub fn overlapping_hint_name<'a>(bbox: &chrys_core::BoundingBox, hints: &'a [chrys_source::RegionHint]) -> Option<&'a str>`.
It computes the intersection of the two rectangles in `u64` integer
arithmetic and returns the hint's name when the overlap is at least half
the box's own area. Use integer arithmetic throughout, with no `f32` and no
`f64` anywhere in this file: the validation contract states that a floating
point comparison discovered inside the evaluator is a signal to route it
through the integer discipline phase 1 established, not to add a new
determinism proof for it. The majority-wins rule mirrors
`chrys_core::classify::kind::majority_block_offset`'s own idiom rather than
inventing a second convention for the same question.

Then `pub fn evaluate(verdict: &chrys_core::Verdict, hints: &[chrys_source::RegionHint], rules: &LoadedRules) -> RuleOutcome`.
For a `Changed` verdict it walks the regions in order and produces one
`RegionOutcome` per region: `Tolerated { rule_index }` when some rule of
the same kind, whose scope the region's box falls inside, holds its
tolerance; `Violation` otherwise. `RuleOutcome` carries that vector and a
`pub fn is_clean(&self) -> bool` that is true when it holds no `Violation`.
An `Identical` verdict produces an empty outcome. A `Refused` verdict
produces an empty outcome too, and the caller must not read that as a pass:
a rule tolerates a change, and a refusal is not a change. Say that in the
function's own doc comment.

**The CLI.** Add `--rule <PATH>` to the `compare` subcommand. When it is
absent nothing changes at all, which is CLI-03's regression guard: the
flag-less path keeps printing what it printed and exiting as it exited.
When it is present, call `load_rules` once before the comparison, so a bad
rule file fails before any image is decoded, then call `evaluate` per frame

clean ranks 0, a `Changed` verdict with a violation keeps ranking 1,
`Identical` stays 0, and `Refused` stays 2. A refusal is never tolerated by
a rule. Keep the existing rule that a sequence's exit code is the worst
rank across every frame.

Complete RULE-01: a tolerance is scoped by the kind of change it names, for
all five kinds, and a tolerance that does not belong to its kind is
refused.

**What the engine actually publishes bounds this.** `chrys_core::Region`
carries `kind`, `bbox`, `offset_px` (set only for `Moved`) and
`colour_delta` (set only for `Recoloured`). There is no published size
delta and no published pixel count. The research recommended a
`max_size_delta_fraction` field for `resized`; it cannot be evaluated from
anything the engine makes public, and computing it would mean reaching into
the engine, which D-03 forbids. Use the bounding box's own area instead,
which is published, and say so in the field's own doc comment so a later
reader knows the field is what the data supports rather than what somebody
preferred.

**Fill out `Tolerance`.** Add a `MaxOffsetPx(u32)` variant and a
`MaxAreaPx(u64)` variant beside Task 1's `Colour` and `Allow`. Then define,
in one place, the table of which rule file fields are valid for which kind:
`moved` takes `max_offset_px` or `allow`; `recoloured` takes `max_delta_e`
and `max_alpha_delta`, or `allow`; `added`, `removed` and `resized` take
`max_area_px` or `allow`. The validation pass refuses a row carrying a
field outside its own kind's set, and refuses a row carrying `allow`
alongside a numeric tolerance, because those two statements contradict each
other. Report the refusal with the line the offending field's own
`toml::Spanned` reports, not the line the enclosing table starts on. Task 1
put the spans in place precisely so this message can be exact.

**Evaluate each kind.** A `Moved` region is tolerated when both components
of its `offset_px` are within the limit in absolute value; a region of kind
`Moved` whose `offset_px` is `None` is a violation, not a pass, because a
rule cannot tolerate an offset it was never told. A `Recoloured` region is
tolerated when its `colour_delta.delta_e` is at or below `max_delta_e` and
the absolute difference of the two colours' fourth bytes is at or below
`max_alpha_delta`; a region of kind `Recoloured` whose `colour_delta` is
`None` is a violation for the same reason. An `Added`, `Removed` or
`Resized` region is tolerated when its box area is at or below
`max_area_px`. `Allow` tolerates any region of its own kind inside its own
scope.

A rule never tolerates a region whose kind it does not name. Test that
directly: a `moved` rule with a large offset limit, and a `Recoloured`
region in the same scope, gives a violation.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| rule file to reader | A `.toml` rule file is a local file this project's code did not write. Its whole document shape, every key and every value is untrusted. In a repository whose rule file can be changed by a pull request from a fork, it is attacker-reachable. |
| rule to exit code | A rule decides whether a real change passes a CI gate. A rule that tolerates more than its author meant is a gate that reports green over a regression. |
| rule crate to engine | Only already-public `Verdict`, `Region`, `ChangeKind` and `ColourDelta` values cross, in one direction. The engine reads no rule. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Denial of Service | `load_rules` | high | mitigate | A crafted rule file of arbitrary size would be read whole into memory before the parser could object. `MAX_RULE_FILE_BYTES` is checked against `std::fs::metadata` before the read, the same posture and limit `hints.rs` already takes, and both the over-limit refusal and the at-limit acceptance are tested. |
| T-03-02 | Tampering | the rule schema | high | mitigate | A rule field that could hold an expression, a shell string or a reference to another rule would make a rule file able to compute, which RULE-03 forbids and which the project's Out of Scope table names as a rule file that can lie. The schema holds eight literal-valued fields, `deny_unknown_fields` closes it, and `rule_row_has_no_computable_field` fails when a ninth appears. |
| T-03-03 | Tampering | the tolerance evaluation | high | mitigate | A colour tolerance that read only `delta_e` would tolerate a change from opaque to fully transparent, because Lab has no alpha axis. The engine's own `ColourDelta` doc comment states this and names this phase. `Tolerance::Colour` carries a separate alpha limit that defaults to 0, and a named test proves the violation. |
| T-03-04 | Spoofing | an unscoped rule | medium | mitigate | A rule with no scope is a global threshold wearing a rule's clothes, and it silences changes nobody named. `Scope` has two variants and no `Option`, so the shape cannot be deserialized (D-01), and `an_unscoped_rule_is_refused` is the named test. |
| T-03-05 | Tampering | a misspelled key | medium | mitigate | A misspelled tolerance key would otherwise deserialize into a default and produce a rule that tolerates nothing or everything without saying so. `deny_unknown_fields` on both the document and the row makes it a loud failure that names a line. |
| T-03-06 | Elevation of Privilege | `chrys-core`'s dependency graph | medium | mitigate | `chrys-rule` depends on `chrys-core`, never the reverse, so `serde` and `toml` stay out of the engine's graph. `cargo tree -p chrys-core -e normal` is checked in this plan's verification, and the engine tree object id is checked after every task. |
| T-03-07 | Repudiation | a refused pair under a rule file | medium | mitigate | If a rule could tolerate a `Refused` verdict, a pair the engine could not register would pass a gate. `evaluate` returns an empty outcome for a refusal, `Refused` keeps ranking 2, and the doc comment states that an empty outcome is not a pass. |
| T-03-SC | Tampering | crates.io installs | low | accept | This plan introduces no new external package. `toml`, `serde` and `thiserror` are all already pinned in the workspace table and all carry an `OK` verdict in `01-RESEARCH.md` or `02-RESEARCH.md`'s Package Legitimacy Audit. No `[ASSUMED]` or `[SUS]` package is adopted, so no legitimacy checkpoint is required. |
