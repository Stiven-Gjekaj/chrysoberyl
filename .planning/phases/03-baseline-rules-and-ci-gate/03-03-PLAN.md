<objective>
Write the report artifact a CI job keeps, and make it name the file each
frame came from.

Success criterion 6 states the defect plainly: phase 2 printed a zero-based
index beside files a producer named from one, and no fixed offset fixes
that, because the producer names the files. The committed
`tests/golden/sequence-01` pair is exactly that shape: eleven files named
`frame1.png` through `frame11.png`, reported as indices 0 through 10.

Purpose: CLI-02, success criterion 6, and CLI-04's workspace-wide guard.

Output: a defaulted `Source::load_named`, a `--report <PATH>` flag writing
a TOML artifact, and a static guard that every direct image-reader call
site is one of the two this project already knows about.
</objective>

## What criterion 6 costs, stated plainly

`03-RESEARCH.md`'s Pattern 5 recommends adding a `source_name: String`
field to `chrys_source::Frame`. That was measured at planning time and
rejected. The command
`grep -rn "Frame {" crates/chrys-core --include="*.rs" | wc -l` reports 45
occurrences across 13 files under `crates/chrys-core/`. A new required
field on `Frame` means editing every one of them. D-03 says phase 3 changes
no file under `crates/chrys-core/`, and the research's own headline claim
says the same. The two halves of that document disagree with each other,
and this plan takes the half that matches the decision.

The route this plan takes instead is a defaulted method on the `Source`
trait. That still touches `chrys-source`, which **is** in the engine's
dependency graph, so it is a real decision and not a free one. Here is what
it costs and what it does not:

- It adds no dependency. The default body uses `std::path` only, which the
  crate already imports, so `chrys-source` still depends on nothing outside
  the standard library and `crates/chrys-source/tests/manifest.rs` still
  passes.
- It adds no field to `Frame`, so no `Frame { .. }` literal anywhere in the
  workspace changes.
- It adds no required method, so `crates/chrys-core/tests/refusal.rs`,
  which imports `Source`, compiles unchanged.
- It puts the name where the knowledge already is. The CLI knows the path
  it was given. The sequence adapter knows the sorted file list. The engine
  knows neither and does not need to.

The one thing it gives up: a `Frame` handed around on its own no longer
carries its file name. Nothing in this project does that today, and the
CLI is the only caller that needs a name.

Carry a frame's own file name from the adapter that read it to the report
that names it, in one commit. Nothing under `crates/chrys-core/` changes

**The trait method.** Add to `chrys_source::Source` a second method,
`fn load_named(&self, path: &Path) -> Result<Vec<(String, Frame)>, Self::Error>`,
with a default body. The default calls `self.load(path)`, takes the path's
own file name once, and pairs every frame with a clone of it. That default
is correct for `RasterSource`, which returns one frame from one file, and
it is correct and honest for `AnimationSource`, whose frames are composited
out of one container and have no file of their own. Fall back to the whole
path's display form when a path has no file name component, so the method
never returns an empty label.

Keep `chrys-source` free of dependencies. The default body needs
`std::path` only, which this crate already imports. Do not reach for
`thiserror`, `serde` or anything else here: `chrys-core` depends on this
crate, so a dependency added here lands in the engine's graph, and
`crates/chrys-source/tests/manifest.rs` is the guard that says so.

Write the method's own doc comment to carry the reason it exists, because
the alternative is the thing a later reader will reach for first: a
`source_name` field on `Frame` would put the name on the type, and it would
require a new field on 45 struct literals under `crates/chrys-core/`, which
this phase may not touch.

**The sequence override.** Override `load_named` in
`impl Source for SequenceSource`. It lists the directory once, decodes once,
and returns each frame beside its own file's name. Then rewrite `load` to
call `load_named` and drop the names, so there is exactly one listing path
and one decode path. Two independent computations of the same sorted order
would be two things that can drift, and the pairing between a frame and its
name is precisely what must not drift. Make whatever in `sequence.rs` needs
to be reachable reachable; the natural-order sort itself does not change.

**The CLI.** Replace `frames_for` with a function returning
`Vec<(String, Frame)>` through `load_named`, and keep the same three-way
dispatch on directory, sniffed animation and single raster file. Split the
names off where the engine is called: `compare_sequence` still receives
`&[Frame]` and is not touched.

Add `--report <PATH>` to the `compare` subcommand. It composes with every
existing flag and changes no exit code and no stdout. When it is absent

**The report.** Create `crates/chrys-cli/src/report.rs` holding the report

report structs live in `chrys-cli` and nowhere else: phase 1's own
responsibility map assigned the file-writing form of a verdict to the CLI
and deferred it to this phase.

The document holds a `meta` table with the base path, the candidate path
and, when `--rule` was given, the rule file's path. Then an array of tables
named `frame`, one per compared index, each carrying `index`, `source` and
`verdict`, where `source` is the base side's own file name from
`load_named` and `verdict` is one of `identical`, `changed` or `refused`.

nobody needs. CLI-01 makes the interesting runs the non-zero ones, so the

**Write it before the exit code is returned.** Restructure `run_compare` so
the report is written on every path that produced verdicts, including the

caller asked for and did not get is a silent hole in a CI job's evidence,

existing behaviour that an error goes to stderr and stdout stays parseable.

`skip_serializing_if` so the difference is carried by the file rather than

  <action>
CLI-04 says every decode call sets an explicit memory limit. That is true
today at every call site, and it stays true only as long as nothing opens a
reader without going through `decode_guarded`. Make it a test rather than a
habit.

**Where the guard lives, and why it is not shared.** Put it in
`crates/chrys-cli/tests/decode_limits_guard.rs`. `chrys-cli` already
depends on every adapter crate, and it is not the engine.
`crates/chrys-core/tests/determinism.rs` already holds a
`strip_comments_and_strings` helper of exactly the right shape, and this
guard cannot import it: it is a test-target-private function inside the
engine's own directory, and D-03 forbids editing anything there to export
it. Write a smaller stripper in the new file, covering line comments, block
comments including nested ones, and ordinary string literals. State this
duplication in the file's own module comment, with the reason, rather than
leaving a later reader to find two strippers and wonder which one is
authoritative. Extracting a shared helper into a dev-only crate would cost
more review than it saves for one hundred lines used twice.

**The allow list.** Two entries, each with the count of call sites it holds
and the reason it is allowed:
`crates/chrys-source-raster/src/decode.rs`, two sites, because
`decode_guarded` applies the limits and `probe_dimensions` deliberately
reads only the header so a `TooLarge` error can report the true size;
`crates/chrys-source-animation/src/lib.rs`, one site, the animation
adapter's own guarded decode. Both counts were measured at planning time
with a search over the current source.

**Assert both directions.** A guard that only fails when a count grows
stops measuring when a file is renamed or its call site is refactored away,
and then it reports green about a file it is no longer reading. Assert the
exact count per allow-listed file, so the guard goes red when a count moves
either way, and assert that every allow-listed path exists. On failure name
the file, the expected count and the found count. On an unexpected site,
name the file that holds it and state the rule it breaks: a decode that
does not go through `decode_guarded` reopens the decompression-bomb risk
CLI-04 exists to close.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| report file to CI job | The report is an artifact another program reads and acts on. A report that is missing, truncated or silently wrong makes a CI job report something that did not happen. |
| file names to the report | A frame's name comes from a file path a caller supplied. It is copied into a document another program parses. |
| workspace source to the decode guard | The guard's own subject is this repository's source text, and its silence is read as evidence that every decode is bounded. |
