say which area a tolerance covers, for an area no rectangle describes.

genuinely new input this phase reads, so it arrives with the same
discipline every other file this project reads already has: one guarded
decode entry point, an explicit memory limit, and a refusal for a path that
tries to leave the directory it was named from.

Purpose: RULE-02's mask half, RULE-04's shipped example, and CLI-04's
extension to the one new decode call site this phase adds.

Output: a mask loader, the white-and-opaque membership rule taken before
planning (D-02), a path-traversal refusal, two committed mask fixtures, and
`examples/rules/example.toml`.

**The dependency.** Add `chrys-source-raster` by path to
`crates/chrys-rule/Cargo.toml`. That is the whole of this plan's dependency
work: no new external package enters the workspace. `chrys-rule` reads a
mask through that crate's already-guarded entry point and never opens a
reader of its own. Plan 02 of phase 2 recorded this as a pattern: an
adapter never opens its own decoder, because it keeps the untrusted-input
boundary in one file rather than one per format. A rule engine is subject
to the same rule.

**The loader.** Create `crates/chrys-rule/src/mask.rs` with
`pub fn load_mask(path: &Path, limits: &chrys_source_raster::DecodeLimits) -> Result<Mask, RuleError>`.
It calls `chrys_source_raster::decode::decode_guarded(path, limits)` and
`chrys_source_raster::normalize::normalize_to_rgba8`, then reduces the RGBA8
buffer to a `Mask` holding one boolean per pixel plus the width and the
height. Taking `limits` as a parameter rather than hard-coding the default
is what lets a test prove the limit is applied instead of ignored;
`load_rules` calls it with `DecodeLimits::default()`, which is the same
512 MiB allocation ceiling and the same 16384-pixel side limit every other
decode in this project already uses (CLI-04).

**The membership rule is D-02, taken before planning. Implement it exactly.**
A mask pixel counts as tolerated when its red, green and blue bytes are all
at or above `TOLERATED_CHANNEL_FLOOR`, which is 250, AND its alpha byte
equals `TOLERATED_ALPHA`, which is 255. White alone is not enough. Write
the reason in the constant's own doc comment, because a later reader will
otherwise take the alpha term for excess caution: a mask drawn as white on
transparency holds the bytes 255, 255, 255, 0 everywhere outside the drawn
area, so a rule that ignored alpha would tolerate the whole canvas without
ever saying so. Phase 1 settled that alpha is part of what "changed" means,
and this is that decision reaching the mask.

**Membership of a box.** Add `pub fn tolerates(&self, bbox: &chrys_core::BoundingBox) -> bool`
to `Mask`. It counts the tolerated pixels inside the box and returns true
when that count is at least half the box's own area, the same majority rule
`overlapping_hint_name` already uses for a named region, so a reader learns
one convention rather than two. Count in `u64` integer arithmetic. This
file holds no `f32` and no `f64`, for the reason plan 03-01 records for
`evaluate.rs`.

A box that reaches outside the mask is clamped to the mask for the count
but not for the area, so a box half outside the mask can never be
tolerated by pixels that do not exist. State that in the doc comment.

**Size agreement.** A mask whose width or height differs from the frame's
is refused, with a message naming both sizes. Do not scale, do not crop and
do not pad. Refusing rather than guessing is the precedent
`chrys_core::RefusalReason::DimensionMismatch` already set for a pair of
frames, and the same reasoning applies: a mask that does not fit the frame
is a question the tool cannot answer. The check needs the frame's size, so
`evaluate` performs it when it applies a mask-scoped rule.

**Loading, not evaluating.** `load_rules` resolves and decodes every
`Scope::Mask` path while the rule file loads, and stores the decoded masks
in `LoadedRules` beside the rules. Plan 03-01 built `LoadedRules` and
`load_rules` for exactly this, so `evaluate`'s signature does not change.
This ordering matters for more than tidiness: a rule file naming a missing
or unreadable mask fails before any image is decoded and before any
comparison runs, so a broken rule file never produces a partial verdict.

**Evaluation.** Extend `evaluate` so a rule whose scope is a mask matches a
region when `Mask::tolerates` is true for that region's box, then applies
the same kind-scoped tolerance plan 03-01 and its task 2 already built. A
mask changes which regions a rule applies to. It never changes what the
tolerance means.

**The fixtures.** Extend `write_rule_01()` in
`crates/chrys-source-raster/examples/make-fixtures.rs` to also write
`tests/golden/rule-01/masks/`. Write `badge.png`: a canvas of `WIDTH` by
`HEIGHT` filled with transparent black, with `paint_rect` painting fully
white opaque pixels over a rectangle that contains `STRUCTURED_RECTS[0]`'s
own rectangle with a margin, matching the `badge` region the hints sidecar
already names. Write `white-on-transparency.png`: the same canvas size,
filled everywhere with the bytes 255, 255, 255, 0, and nothing painted on
it. That second file is not a curiosity. It is the exact failure D-02
names, committed so the decision is checked by a test rather than believed.

Write two rule files beside them: `mask-tolerate.toml`, holding the same
kind and the same measured tolerance plan 03-01 recorded for

`mask-transparent.toml`, identical except that it names
`masks/white-on-transparency.png`. The first exits 0. The second exits 1,
because a mask that is opaque nowhere tolerates nothing. Commit all four
files.

  <action>
A rule file is structured input read as data, and after this plan it holds
a file path. A path is the one field in this schema that reaches outside
the document. Close it here.

`03-VALIDATION.md` states the rule: a mask resolves relative to the rule
file's own directory and must not escape it. That is the same convention
`hints.rs` already uses for a sidecar, which resolves next to its image
rather than next to the process's current directory, so a rule file behaves
the same whichever directory a person runs the tool from.

**Two checks, not one, and both of them.** The first is lexical and runs
before the file system is touched: refuse a path that is absolute, and
refuse a path holding any parent-directory component. This one produces the
clear message, and it refuses without reading anything at all, which is
what makes a hostile path cost nothing. The second is a canonical check
that runs after: canonicalize the rule file's own directory and the
resolved mask path, and refuse when the mask's canonical path does not sit
inside the directory's canonical path. The first check alone cannot see a
symbolic link that points outside; the second can. Phase 1 recorded that a
source-level guard is defence in depth for one that depends on the
environment, and this is the same shape of pairing.

Give the refusal its own `RuleError` variant carrying the rule file's own
directory and the offending path, so a person reading the failure learns
both which boundary was crossed and what crossed it. Do not fall back to
reading the file, do not silently drop the rule, and do not canonicalize
first and ask afterwards.

**The tests.** Create `crates/chrys-rule/tests/mask.rs`. Each test builds
its own temporary directory holding a rule file, and where a mask is
needed, writes one. Cover, each as its own named test: a path shaped like
`../../etc/passwd`; a path with a single leading parent component; an
absolute path; a symbolic link inside the rule file's directory pointing to
a file outside it; a path naming a file in a subdirectory below the rule
file, which is accepted; and a mask that decodes but whose size exceeds a
`DecodeLimits` value the test supplies, which is refused by the guarded
decoder. Name the traversal test so its intent survives a later reader:
this is the case `03-VALIDATION.md` asked for by name.

Skip the symbolic-link test on a platform where creating one needs a
privilege the test process does not have, and say so in the skip message
rather than passing silently. A test that quietly does nothing is the
failure mode phase 2 recorded for a command that selected no test.

Assert on the message as well as the variant. A refusal a person cannot act
on is a refusal that gets worked around.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| rule file to file system | The `mask` field is a file path inside an untrusted document. It is the one field in this schema that reaches outside the document. |
| mask image to decoder | A mask is an image file the project's code did not write, on the same terms as any other input image. |
| mask pixels to tolerance | The mask's own bytes decide which changes a CI gate stops reporting. A mask read too generously is a gate that reports green over a regression. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-08 | Information Disclosure | the `mask` path | high | mitigate | A rule file changed in a pull request from a fork could name `../../etc/passwd`, or an absolute path to a secret, and have a CI job read it. The path resolves relative to the rule file's own directory; a lexical check refuses an absolute path and any parent component before any file is opened, and a canonical check refuses a path that reaches outside through a symbolic link. Both are tested, including the accepted case. |
| T-03-09 | Denial of Service | `load_mask` | high | mitigate | A crafted mask declaring an enormous size would force an unbounded allocation. The mask decodes through `chrys_source_raster::decode::decode_guarded` with `DecodeLimits`, the same CVE-2023-29408-class mitigation every other decode in this project already carries, and `a_mask_above_the_decode_limits_is_refused` proves the limit is applied rather than assumed (CLI-04). |
| T-03-10 | Tampering | the mask membership rule | high | mitigate | A convention that read only the colour channels would treat a mask drawn as white on transparency as tolerating the whole canvas, silencing every change in the frame with no error anywhere. D-02 requires white AND opaque; `white-on-transparency.png` is committed as a fixture and its rule file must exit 1. |
| T-03-11 | Spoofing | a mask of the wrong size | medium | mitigate | A mask smaller than the frame, scaled or padded to fit, would tolerate an area its author never drew. A size mismatch is refused with both sizes named, following the engine's own `DimensionMismatch` precedent, and no scaling, cropping or padding happens anywhere. |
| T-03-12 | Denial of Service | a partly applied rule file | medium | mitigate | A rule file whose third mask is missing would otherwise fail after two rules had already been applied to a running comparison. `load_rules` decodes every mask while the file loads, so a bad rule file fails before any image is decoded and no partial verdict is produced. |
| T-03-13 | Elevation of Privilege | `chrys-core`'s dependency graph | medium | mitigate | `chrys-rule` now depends on `chrys-source-raster`, a crate holding a format decoder. The direction is what keeps this safe: `chrys-core` depends on neither. `cargo tree -p chrys-core -e normal` is checked in this plan's verification, and phase 1 recorded that a re-export once carried a banned dependency past a manifest check, which is why the check reads the resolved tree and not the declared list. |
| T-03-SC | Tampering | crates.io installs | low | accept | This plan introduces no new external package. The one dependency it adds, `chrys-source-raster`, is a workspace crate this repository wrote. No `[ASSUMED]` or `[SUS]` package is adopted, so no legitimacy checkpoint is required. |
