<objective>
Let a person say, once and explicitly, that a candidate is now the truth,
and let every later comparison reach that truth by name.

A baseline that updates itself stops being a baseline. This project's own
Out of Scope table says so. The whole design of this plan follows from that
one sentence: one subcommand writes, everything else reads, and a name that
nobody accepted is an error rather than an opportunity.

Purpose: BASE-01, BASE-02, BASE-03, BASE-04, and CLI-03's regression guard
across the positional-argument change `--baseline` needs.

Output: the `chrys-baseline` crate, an `accept <NAME> <PATH>` subcommand, a
`--baseline <NAME>` flag on `compare`, and a real committed manifest in
this repository.
</objective>

## Where the store lives

The default store root is `chrys-baselines/` in the current directory, and
`--store <DIR>` overrides it so a test never writes into the repository.
The name is `chrys-baselines`, plural, so it does not read as the crate
directory `crates/chrys-baseline`. It is a plain directory at the top of
the repository rather than a hidden one, because BASE-01 wants a person to
find the manifest and read its diff in a pull request. `.gitignore` holds
no rule that would exclude it, which was checked at planning time by
reading that file.

**The crate, and what it must not know.** Create `crates/chrys-baseline`.
Its dependency table takes `toml`, `serde` with its `derive` feature, and
`thiserror` from the workspace table, and nothing else. It does not depend
on `chrys-core` and it does not depend on `chrys-source`. A baseline store
resolves a name to a path and records digests somebody else computed; it
has no business knowing what a pixel is, what a `Frame` is or what a
verdict is. Keeping that true is what makes BASE-03's "a second backend
needs no change to the engine" a structural fact rather than a hope, and it
is checkable: the crate's own manifest names neither workspace crate.

**The trait.** `pub trait BaselineStore` with an associated `Error` type
and exactly two methods.

`resolve(&self, name: &str) -> Result<PathBuf, Self::Error>` returns the
path of the currently accepted baseline named `name`. It is read only by
contract, and the doc comment says so.

`accept(&self, name: &str, candidate_path: &Path, frame_digests: &[(String, String)]) -> Result<(), Self::Error>`
records the digests as the new baseline for `name` and copies
`candidate_path`, a file or a directory, into the store. Each pair is a
source file name and a lowercase-hexadecimal digest, in frame order. The
caller has already decoded and already hashed; this trait decodes nothing.

Two methods, no more. A third would be a place for a backend to differ in a
way the CLI would then have to know about.

**The golden-file backend.** `GoldenFileStore { root: PathBuf }` stores a
baseline named `name` at `<root>/<name>/`, holding the accepted file or
directory contents under their own original names, and keeps
`<root>/MANIFEST.toml` beside them. The manifest holds an array of tables
named `baseline`, each with a `name`, and inside it an array of tables
named `frame`, each with a `source` and a `digest`. A single accepted
change to one frame of one baseline then changes exactly one `digest` line,
which is what makes the diff readable in a pull request without opening the
image.

`resolve` finds a baseline by listing `<root>/<name>/` rather than by
trusting the manifest's `source` value. A person who renames the stored
file with `git mv`, while it stays inside its own directory, keeps a
working baseline; the identity a person tracks is the name, not a path. A
directory holding exactly one file resolves to that file's own path, so the
CLI loads it as a single raster image. A directory holding more resolves to
the directory itself, so the CLI loads it as a sequence. Reuse the reading
discipline `hints.rs` already established for the manifest: bound its size
from `std::fs::metadata` before reading, set `deny_unknown_fields`, and
report a parse failure with the message `toml` produces, which names a
line.

**Put every write in one function.** `accept` performs its work through a
single private function in `golden.rs`. Every call that creates a
directory, copies a file, writes a file or removes one lives inside that
one function's body and nowhere else in the crate. Task 3 turns that into a
guard; building it this way now is what makes the guard cheap and the
property true rather than nearly true.

**The CLI: accept.** Add `chrys accept <NAME> <PATH> [--store DIR]`. It
loads `PATH` through the same `load_named` path `compare` uses, so a
directory accepts as a sequence and a file accepts as one frame, computes
`chrys_core::hash::rgba8_digest` over each decoded frame's own RGBA8 bytes,
and calls `GoldenFileStore::accept` once with the name, the path and the
digest list. This is the only call site of `accept` in the whole workspace.
Do not add a second one, and do not add a convenience path anywhere that
accepts on a person's behalf.

**The CLI: compare.** Add `--baseline <NAME>` and `--store <DIR>` to
`compare`. `--baseline` supplies the base side from the store, so the
positional arguments change shape. Replace the two positional arguments
with one list of paths taking one or two values, and validate the count
explicitly: with no `--baseline`, exactly two paths are required and they
are the base and the candidate in that order; with `--baseline`, exactly
one path is required and it is the candidate, because the base comes from
the store. Any other count is an error that says which form was used and
how many paths it needs. Do not let clap guess, and do not let one
positional silently take the other's place.

`compare BASE CANDIDATE` must keep printing exactly what it prints today
and exiting exactly as it exits today. That is CLI-03's regression guard,
and `crates/chrys-cli/tests/digest.rs` is what proves it across this
change.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| candidate to store | An accept copies a file or a directory the caller named into a location the repository commits. The path and the contents are whatever the caller supplied. |
| manifest to comparison | `MANIFEST.toml` is a committed file a person can hand-edit. Its digests are read back and used to judge a stored baseline. |
| store to CI verdict | A baseline is what every later comparison is measured against. A wrong or silently changed baseline is a gate that passes a regression forever. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-20 | Elevation of Privilege | an implicit first accept | high | mitigate | A convenience path that accepted the candidate when no baseline existed would turn every new name into an unreviewed acceptance, which is the automatic drift this project's Out of Scope table forbids. `resolve` errors on an unaccepted name, the `accept` subcommand is the only call site of `BaselineStore::accept`, and both a behavioural test and a static guard hold it (BASE-04). |
| T-03-21 | Tampering | `MANIFEST.toml` | high | mitigate | A hand-edited manifest claiming a digest that does not match its stored file would make a green run mean nothing. The CLI recomputes each digest with `chrys_core::hash::rgba8_digest` after decoding the resolved baseline and fails the run naming both digests. `resolve` itself never trusts the manifest, so a store that cannot be parsed cannot silently resolve either. |
| T-03-22 | Tampering | `resolve` | high | mitigate | A `resolve` that wrote anything would be a second, unnamed path into the store. Every write in `chrys-baseline` lives inside one private function called from `accept` alone, proven by a static guard and by a behavioural test that records the whole path set with lengths and modification times, both drilled red before they are trusted. |
| T-03-23 | Denial of Service | the manifest parse | medium | mitigate | A manifest of arbitrary size, or one holding unknown keys, arrives from the same place the rest of the repository does. The manifest is size-bounded from `std::fs::metadata` before it is read and parsed with `deny_unknown_fields`, the same posture `hints.rs` and `chrys-rule` already take. |
| T-03-24 | Tampering | the recursive copy in `accept` | medium | mitigate | Following a directory entry that is not a regular file, or recursing into a nested directory, would copy something the caller did not name into a committed store. The walk copies regular files only and does not recurse, matching the rule the sequence adapter's own `list_sorted` already applies. |
| T-03-25 | Repudiation | a mistaken accept | medium | accept | Nothing downstream can tell a correct accept from a mistaken one, and `03-VALIDATION.md` records this as a process risk rather than a code defect. The roadmap puts the real mitigation in phase 6's accept-and-reject window. | T-03-26 | Elevation of Privilege | `chrys-core`'s dependency graph | medium | mitigate | `chrys-baseline` depends on neither `chrys-core` nor `chrys-source`, so no direction of dependency exists in which a store could reach the engine. `cargo tree -p chrys-baseline -e normal` is checked, and the engine tree object id is checked after every task. |
| T-03-SC | Tampering | crates.io installs | low | accept | This plan introduces no new external package. `toml`, `serde` and `thiserror` are taken from the workspace table where they are already pinned and already audited.
